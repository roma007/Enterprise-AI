## [0.28.0] · 2026-11-02 · PostgreSQL 与多实例（C4 / D7）

### C4 PostgreSQL 双后端
- `app/db.py`：`DATABASE_URL` 切换 SQLite / PostgreSQL，统一连接/事务/占位符
- 兼容处理：`?`→`%s`、`INSERT OR IGNORE/REPLACE`→`ON CONFLICT`、`rowid`→`ctid`
- `init_db()` PG 分支：advisory lock 串行化 DDL，多实例同时启动不死锁
- `scripts/migrate_to_pg.py`：dry-run、幂等 upsert、依赖顺序、行数校验、
  阈值文件迁移；复制 12 张表
- 修正 PG 差异：`MAX(a,b)`→`CASE`、`AVG` 的 Decimal 转 float

### D7 多实例任务队列
- `jobs` 表：`pending/running/done/failed` + `worker` + `lease_until` + `params_json`
- 每个实例一个 worker，抢到任务才处理；租约过期自动被其他实例接手
- 批次项逐条抢占，避免两个实例重复处理同一条
- 取消改 `batches.cancel_requested`，跨实例生效
- 被接手时（attempts>1）强制回收 `processing` 项，避免卡死
- 回写发件箱改为行级抢占，多实例不会重复发送
- PG 阈值存 `app_settings`，多实例 2 秒内同步
- `GET /api/admin/jobs` 查看任务与 worker

### 实测（真实 PostgreSQL 16）
- 迁移：259 runs / 150 batch_items / 56 sessions 等 12 张表行数全部一致
- PG 单实例：31 项 API 验收全通过
- 双实例：2 个批次分给 2 个 worker，各 15/15 完成
- 跨实例取消：处理中 2 条 → 取消 → 3 条后停，97 pending；续跑 100/100
- 进程被杀：租约 10s，另一实例 11.8s 接手，attempts=2，120/120 完成
- 并发抢占：6 个 worker 只有 1 个抢到；发件箱 3 条无重复领取
- 5 个实例同时 init_db 无死锁
- SQLite 回归：smoke 15 项全绿；三样本集 100%/98.7%/100%

## [0.26.0] · 2026-11-02 · 单实例上生产加固（D1/D2/D3/D6）

### D1 WAL + 安全备份
- 数据库切换 `journal_mode=WAL`、`synchronous=NORMAL`
- 连接改为用后即关（之前靠 GC，WAL 下会阻止 checkpoint）
- `scripts/backup_db.py`：SQLite 在线备份 API，校验 `integrity_check` 与行数，保留最近 N 份
- `make backup`；恢复步骤写进运维手册
- **不再建议 `cp copilot.db`**：WAL 下会丢最新写入

### D2 外键
- 每个连接 `PRAGMA foreign_keys=ON`
- 启动时清理历史孤儿（本次清掉 2 条 `run_id=''` 的 feedback）
- 新库 schema 为 feedback / run_revisions / learn_queue / user_sessions / batch_items 加外键
- 老库不重建表，只启用已声明的外键（文档写明）

### D3 登录失败锁定
- `login_attempts` 表：同一 邮箱+IP 在窗口内失败 N 次 → 锁定 M 秒
- 默认 5 次 / 15 分钟，环境变量可调
- 返回 429 + `Retry-After`
- 未知邮箱也执行一次 scrypt，避免按响应时间枚举账号

### D6 数据保留
- `scripts/cleanup.py`：默认 dry-run
- 清理过期会话、已结束发件箱、过期登录记录
- 业务数据（runs/feedback/金标）默认不动，需 `--runs-days` 显式开启

### 实测
- WAL 后写入期间读取 p95：22.6ms → 0.5ms
- `foreign_keys=on`；插入无主会话被 IntegrityError 拦住；历史孤儿启动时清理
- 连续 3 次错密码 → 429；锁定期间正确密码仍 429；到期后 200
- 清理脚本 dry-run 不改数据；apply 只删过期行
- 备份 424KB，`integrity_check=ok`，行数一致
- smoke 14 项全绿；三样本集回归未变

### B5 地址校验

  · 只写到城市 / 没有任何落点 → 提醒补全

### B6 异常费用识别
- `app/fees.py` + `/fees` 页面 + `POST /api/fees/check`（财务/管理员）
  · 重复收费：同单号 + 同费用名 + 同金额
  · 金额非法：≤0 或无法解析
  · 算术不符：数量 × 单价 ≠ 金额

```
POST {平台}/api/hooks/copilot/eval
x-copilot-token: <共享 token>
{ idempotency_key, experiment_id, dataset_name, config, metrics, issues, source }
```
指标**只来自服务端 `run_all()`**，不接受调用方填数。

### 设计取舍

## [0.23.0] · 2026-11-02 · 企业微信安全模式（B3）

### 新增
- `app/wecom_crypto.py`：企业微信官方加解密协议
  · `AESKey = Base64_Decode(EncodingAESKey + "=")`
  · 明文结构 `random(16B) + msg_len(4B) + msg + receiveid`
  · AES-256-CBC，IV = AESKey[:16]，PKCS#7 **32 字节块**
  · 签名 `sha1(sort(token, timestamp, nonce, encrypt))`
  · receiveid 校验（防串号）
- GET 回调：安全模式下解密 `echostr` 后原样返回
- POST 回调：解密外层 `<Encrypt>`，处理后再把回复包成加密信封
- `WECOM_ENCODING_AES_KEY` 环境变量；留空仍走明文（本地调试）
- 安全模式缺 token / corpid / aes key 时返回 503，明确缺哪一项

### 设计取舍
- **`cryptography` 是可选依赖**：只有启用安全模式才需要；
  未安装时上传路径不受影响，回调返回「pip install cryptography」
- **明文模式保留**：现场没有 EncodingAESKey 时仍能用，但文档写明仅调试
- **加解密单独成文件**：协议细节多，和消息拼装混在一起很难测
- **拒绝空 token 跑安全模式**：否则等于谁都能伪造回调

### 实测
- 官方文档 POST 示例：签名 `477715d1…` 一致，解密得到 `<Content>hello</Content>`
- URL 验证：加密 echostr → 解密回原文，签名错误 403
- 加密 POST：回复签名可验、可解密，内容含识别出的箱号
- 明文模式：GET/POST 均正常，不影响现有部署
- 官方向量自检已挂进 smoke
- smoke 10 项全绿；三样本集回归未变

- 标注/跳过写入 `run_revisions`（action=`label` / `ignore`），审计可追

### 界面
- 三个视图：待标注 / 已标注 / 已跳过，顶部实时统计
- 字段预填系统抽取值，改过的字段下方标红「已修改」
- 保存后自动跳到下一条，适合批量清理
- 导出按钮：`/api/learn/export.jsonl`，追加到 `samples/` 后重跑评测

### 设计取舍
- **预填而不是空白**：多数单只需确认，直接保存即可；改过的才成为难例
- **`corrected` 由服务端算**：不信任前端传值，避免把难例标成普通样本

- 标注不会改 `runs` 的确认状态，与「确认」是两条独立链路

## [0.21.0] · 2026-11-02 · 撤销与修订流水（B2）

### 新增
- `run_revisions` 表：append-only，记录 `confirm` / `undo` 的完整前后快照
- `POST /api/runs/{id}/undo`：撤销一次确认（**仅管理员**）
- `GET /api/runs/{id}/revisions`：查看一张单的修订历史
- `GET /api/runs/confirmed`：最近已确认、可撤销的单据
- `/history` 页面：确认历史 + 修订明细 + 撤销按钮
- 工作台确认成功后，管理员会看到「撤销确认」按钮
- `GET /api/audit/{id}` 现在附带 `revisions`

### 撤销做了什么
| 对象 | 变化 |
|---|---|
| `runs` | `confirmed=0`、`confirmed_by=''`、`handle_ms/forced` 清空、`version+1` |
| `feedback` | 删除该单的修正明细（被撤回内容完整保存在 `before_json`） |
| `learn_queue` | 金标回到 `pending`，`gold_json` 清空 |
| `run_revisions` | **追加**一条 `undo`，不删任何历史 |

### 设计取舍
- **撤销不是删除**：确认这个动作发生过，删记录等于篡改审计；
  所以只追加反向流水，`before_json` 保存被撤回的字段与金标
- **feedback 直接清空而不是打作废标记**：修正率、字段准确率都按 feedback 统计，
  留一条"已作废但仍在表里"的记录，早晚污染某个没加过滤的查询
- **乐观并发**：撤销可带 `version`，期间有人重新确认则 409，避免撤错版本
- **条件更新**：`WHERE confirmed=1`，两个人同时点撤销只有一个成功
- **仅管理员**：撤销影响已确认数据与金标，单证员/财务越权返回 403

### 实测
- 确认 → revision `confirm v1`；撤销 → `undo v2`，feedback 清空，金标回 pending
- 重复撤销 409；版本不匹配 409；单证员撤销 403
- 撤销后可重新确认（version 3），审计里能看到 confirm→undo→confirm 全链路
- 指标一致：撤销后 `tickets_confirmed=0`、`labeled=0`
- 页面：历史列表、修订展开、撤销 toast 均正常，无控制台报错
- smoke 9 项全绿；三样本集回归未变

  · 实测：703 条台账 / 45 层，抽 400 份覆盖 100%；抽 40 份时明确提示"只能覆盖 40 层"
- **B7 跨批次失败队列**（`/api/batches/failed`、`/retry-all`）
  · 不用一个批次一个批次去翻
  · 一键重排后回到对应批次点"开始处理"即可续跑
  · 批次页顶部常驻失败提示条
