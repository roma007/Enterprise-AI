## [0.11.0] · 2026-11-02 · 04b 发票识别与校验

### 新增
- `app/invoice.py`：复用托书底座（LLM 网关 / OCR / 分级审批 / 留痕），只换 schema 与校验
- `/invoice` 页面与 `/api/invoice/*` 接口
- 行业校验：
  · **统一社会信用代码校验位**（GB 32100，mod 31）——买卖双方都验
  · 金额勾稽：金额 + 税额 = 价税合计（容差 0.02）
  · 税额反算：金额 × 税率 是否等于票面税额
  · 税率合法性、发票号码位数、专票校验码
- 与托书同一套"规则够好就跳过模型"策略

### 实测
- 渲染 3 张发票（干净 / 倾斜+阴影 / 带印章）→ 关键字段 **10/10**，均自动通过
- 结构化发票 27ms（跳过模型）；口语化"一千二百三十四块五毛六" 6.8s（调模型，换算正确）
- 故意改错价税合计 → 立即 `E_AMOUNT_MISMATCH` 阻断

## [0.10.0] · 2026-11-01 · 脱敏与批量导入（采集链路提速）

### 新增
- **P0 脱敏**（`app/masking.py`、`/api/mask`）
  · 公司名 → 客户一/客户二…（持久映射，同一实体始终同一代号）
  · 联系人姓名 → 张*
  · 手机 `138****5678`、固话 `0574-****6666`
  · 身份证/报关单号/银行账号 → 等长占位符；邮箱保留域名
  · 保留原文指纹，可证明"脱敏数据来自哪份原文"
- **P1 批量导入**（`/batch`、`/api/batches/*`）
  · 一次上传最多 200 个文件，后台线程处理
  · 批次状态机：pending → processing → extracted / failed
  · 进度可查、失败可一键重试、断点续跑
  · 处理时可选"采集即脱敏"（存库只存脱敏后内容）

### 修复（过程中发现）
- 公司名正则非贪婪导致「宁波宏图国际贸易有限公司」被切成「客户一**有限公司**」
  → 后缀按长度降序 + 贪婪匹配
- 18 位报关单号先被身份证规则吃掉 → 调整规则顺序
- 联系人姓名原先未脱敏 → 补 `person` 规则

### 效果
采集链路的两个最大工时项（脱敏 6.7h、上传 1.7h）已消除，400 份准备时间约 18.6h → 5.8h。

## [0.9.1] · 2026-11-01 · 资料采集模拟，修 3 处采集链路问题

### 新增
- `scripts/sim_intake.py` / `make intake`：模拟档案室扫描 → OCR → TMS 导入 → 配对 → 标注
- `会客包/09_资料采集模拟.md`：6 个卡点排序与 400 份工时账

### 修复
- **GBK 编码探测失效**：`data.decode('utf-8', errors='ignore') or data.decode('gbk')`
  在 GBK 文件上返回乱码（非空），永不回退 → 改为 strict 逐编码尝试
- **缺少常见字段别名**：「货主」→ client、「封条」→ seal_no、「柜编码/柜别」
- **地址比较口径过严**：空格差异被计为错误，地址类字段比较时统一去空格与标点

### 实测
- 干净扫描 92.2%｜装订阴影 92.2%｜倾斜 93.5%｜**印章遮挡 81.8%**｜折痕+噪点 84.4%
- TMS 导入：GBK + 客户叫法从 0 列映射 → 10 列映射
- 配对：10/10（合成数据，真实数据待复测）

## [0.8.0] · 2026-11-01 · 模拟演练 v2，修 4 个口径 bug

### 修复（**指标类，最危险**）
- 修正率永远 100%：分母用了"被改字段数" → 改为"已确认单的非空字段总数"（100% → 0.4%）
- 两个页面两个自动通过率：风险模拟另算阈值 → 统一用 `review_level`
- 节省工时按"花掉的时间"算 → 改为 `max(0, 基线 − 实际)`（差 74 倍）
- **0 错单被当成 0 风险** → 加 Laplace 平滑 `(错单+1)/(样本+2)`（结论从"支持取消"变成"不建议取消"）
