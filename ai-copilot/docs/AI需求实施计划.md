# AI 需求实施总计划

> 版本：v1.0 ｜ 2026-11-08 ｜ 依据：`会客包/23_协丰与同类企业AI需求地图.md`
> 原则：**先数据后模型，先规则后预测；一批只做一件事，做完有证据再进下一批。**
> 边界：不把规则/脚本包装成大模型；合成数据只做回归，不对外当真实准确率。

## 1. 总路线：四层数据成熟度

```mermaid
flowchart LR
  L1["L1 文档数字化<br/>托书/发票/对账单/聊天"] --> L2["L2 业务结构化<br/>订单/应收/应付/成本"]
  L2 --> L3["L3 过程可视化<br/>港口/船期/报关/在途"]
  L3 --> L4["L4 预测与优化<br/>报价/舱位/调度/信用"]
```

**不能跳级。** 没有 L1 的结构化，L4 的预测就是拍脑袋。

## 3. 每批的范围与验收

### B1 · 文档 AI 完整化

**目标**：把“能读的单据”从托书/发票扩展到对账单/结算单/聊天，并做跨单证一致性。

| 项 | 内容 |
|---|---|
| 已完成 | 对账单文件 OCR（AI-41）、在途事件抽取（AI-42） |
| 已完成 | 单证一致性（AI-43）：托书/发票/对账单的箱号、金额、单号、客户名交叉比对 |
| 验收 | 用 20–50 份真实单据，字段准确率 ≥90%，修正 ≤1.5 分钟/单；一致性检查能定位到具体字段 |
| 不做 | 自动改单、自动入 TMS、自动付款 |

### B2 · 知识库与问答

**目标**：把客户 SOP、合同价、报关口径、异常处理变成可检索、可引用的问答。

| 项 | 内容 |
|---|---|
| 能力 | 文档入库、分块、检索、LLM 回答 + 引用原文；无模型时退化为关键词摘录 |
| 验收 | 20 个真实问题，答案可追溯到原文；答不出时明确说“没有”，不编 |
| 不做 | 通用百科、无关内容、无引用的自由生成 |

### B3 · 报价与成本

**目标**：报价不再靠拍脑袋；能解释“这单为什么不赚钱”。

| 项 | 内容 |
|---|---|
| 能力 | 历史价/成本/舱位检索；报价草稿；单票/线路成本与毛利解释 |
| 验收 | 报价偏差可解释；每个数字能追到价格表或成本记录 |
| 不做 | 自动对外报价、自动锁舱、无数据预测 |

### B4 · 关务与合规

**目标**：HS 归类、申报要素、单证一致性。

| 项 | 内容 |
|---|---|
| 能力 | HS 候选 + 置信度 + 历史依据；申报要素缺项；报关资料互相比对 |
| 前提 | 客户商品库、历史报关记录、报关行口径 |
| 验收 | 建议必须带依据；低置信度转人工；不承诺“归类一定正确” |
| 不做 | 自动申报、替代报关员 |

### B5 · 客户查询与在途

**目标**：客户问“到哪了/几时到/放行没有”，系统能答或转人。

| 项 | 内容 |
|---|---|
| 能力 | 港口/船期/报关/GPS 数据接入；AI 回答 + 引用；答不了转人工 |
| 前提 | 客户/港口/船公司数据接口 |
| 验收 | 回答可追溯到数据源；不编 ETA |
| 不做 | 无数据时的“智能预测” |

### B6 · 调度与装箱优化

**目标**：降低空驶、提高装载率、优化驳船/舱位。

| 项 | 内容 |
|---|---|
| 能力 | 车辆-订单匹配、路线、拼箱/装箱、舱位匹配 |
| 类型 | 运筹优化 + 规则，不是 LLM |
| 前提 | 订单/车辆/GPS/舱位/货物尺寸 |
| 验收 | 与人工方案对比，空驶/装载率有可量化改善 |
| 不做 | 无数据、无约束的“AI 调度” |

### B7 · 预测与信用

**目标**：运价/舱位、回款、客户信用。

| 项 | 内容 |
|---|---|
| 能力 | 时序/分类模型；可解释；人工兜底 |
| 前提 | 12–24 个月历史数据 |
| 验收 | 回测指标 + 业务可解释；不拿合成数据对外 |
| 不做 | 没有历史数据的“预测大屏” |

### B8 · 经营分析增强

**目标**：从“报表”到“结论 + 动作”。

| 项 | 内容 |
|---|---|
| 已完成 | `/insight` 通用版（AI-40）；AI 简报/优先级/动作草稿（AI-53）；公开资料 + 合成运营数据的能源/线路/人力对比（AI-54） |
| 待做 | 真实成本科目、客户/线路盈利、能源/工时/TCO 真实数据、管理驾驶舱 |
| 验收 | 每个结论可追溯到单据/客户/线路；AI 只解读，不把规则指标包装成大模型 |

### B9 · 渠道与交付

**目标**：OEM/白牌、组件化安装、伙伴支持。

| 项 | 内容 |
|---|---|
| 前提 | 2–3 个客户跑通、产品标准化、支持体系 |
| 验收 | 伙伴能独立部署/支持；品牌/配置可替换 |
| 不做 | 现在就做 OEM 分散主线 |

## 4. 执行规则

1. **一批一提交**：每批完成后更新 `内部开发与发布.md`、`VERIFICATION.md`、`CHANGELOG.md`、本文状态。
2. **先规则后模型**：能用规则算的，不交给模型；模型只做读/解释/草稿。
3. **没有数据就标阻塞**：不拿合成数据当客户结论。
4. **每批必须有验收**：字段准确率、工时、差异召回、引用可追溯等，至少一个可复现指标。
5. **不并行**：`verify:write` 与 e2e 不并行；CI 四 job 全绿再进下一批。
6. **不做清单**：自动付款、自动报关、数字人、无人驾驶、无数据预测。

## 6. 风险

| 风险 | 应对 |
|---|---|
| 功能堆砌，没有价值证明 | 每批只选一个可验收指标；不达标就停 |
| 客户数据拿不到 | 先做通用/合成验证，真实 POC 前不对外承诺 |
| 模型幻觉 | 引用原文；无依据就说没有；规则兜底 |
| 数据安全 | 私有化/脱敏/权限/审计；客户数据不出边界 |
| 组织不配合 | 先找一个岗位/一个人，不铺开 |
