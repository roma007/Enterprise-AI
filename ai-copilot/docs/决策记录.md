# 决策记录（ADR）

> 记录"为什么这么做"，而不是"做了什么"。做了什么看 README 和 CHANGELOG。
> 每条都带**依据**和**怎么复现验证**——半年后想推翻某个决定，先看这里。
>
> 格式：背景 → 选项 → 结论 → 依据 → 复现方式 → 什么时候该推翻。

## ADR-001 · 独立仓库，不与交付平台合并

**日期**：2026-11-01 ｜ **状态**：生效

**背景**：已有「企业 AI 化项目管理系统」（Node/Fastify + PG + React），这里要做的是真实的 AI 应用。

**选项**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 并入现有仓库 | 代码复用、部署简单 | 两套技术栈混在一起；AI 应用的依赖（onnxruntime、模型）会污染交付平台 |
| B. 独立仓库 + HTTP 对接 | 各自演进，部署形态不同（客户侧可能要私有化） | 需要约定接口 |

**结论**：B。通过三个 ID 对齐：`opportunity_id`、指标口径（基线/目标/实测）、`poc_run_id`。

**依据**：运行特征完全不同——交付平台是 CRUD + 报表，AI 应用是长任务 + 模型调用 + 成本敏感。

**什么时候该推翻**：如果最终只有一个客户、且交付平台也要私有化部署，合并成一个仓库可以减少运维负担。

## ADR-002 · 先做可运行 demo，再补计划

**日期**：2026-11-01 ｜ **状态**：已修正

**背景**：最初按"先计划后动手"推进，但使用者提出"手里没东西不敢见客户"。

**结论**：先做能跑的 demo，再补 `会客包/00_实施计划.md`，之后严格按计划执行。

**后续修正**：使用者随后要求"先写完整计划再实施"，于是补齐计划（v1.0）并建立门禁 G0–G4。**这条记录保留，因为它说明了为什么文档晚于代码。**

**教训**：先做 demo 可以，但**计划补完之前不许再扩范围**——否则会变成"想一个做一个"。

## ADR-003 · OCR 选 RapidOCR（方案 B）

**日期**：2026-11-01 ｜ **状态**：生效

**背景**：需要识别微信发来的托书截图和 PDF。

**选项**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. macOS 原生 Vision（`ocrmac`） | 安装小、中文好 | 只能跑 Mac，以后上 Linux 服务器要换 |
| B. RapidOCR（onnxruntime） | 跨平台，可部署到服务器 | 首次装约 100MB |

**结论**：B。使用者明确选择 B。

**踩到的坑**：Python 3.14 没有 onnxruntime 的 wheel，必须用 **Python 3.11** 建虚拟环境。

**什么时候该推翻**：如果只在 Mac 上做演示、永远不上服务器，A 更轻。

## ADR-004 · 模型选 claude-haiku-5-5

**日期**：2026-11-01 ｜ **状态**：生效

**背景**：走 OpenCode Go 网关，可选模型很多。

**实测**（2 份最难的样本：口语改单、单行无分隔）

| 模型 | 准确率 | 单条耗时 |
|---|---|---|
| **claude-haiku-5-5** | 92% | **5.2s** |
| mimo-v2.6-flash | 92% | 10.2s |
| gemini-4-argon | 92% | 14.4s |
| minimax-m3.1-flash | 38% | 11.1s |
| gpt-6-luna | 0%（返回空） | 2.0s |

**结论**：claude-haiku-5-5——同等准确率下最快。

**复现**：换 `LLM_MODEL` 后跑 `make eval` 与 `make simday`。

## ADR-005 · OpenCode 网关的两个必需头

**日期**：2026-11-01 ｜ **状态**：生效

**背景**：接 `https://opencode.ai/inference/go/openai/v1`。

**现象与原因**

| 现象 | 原因 |
|---|---|
| `HTTP 403: error code 1010` | Cloudflare 拦截默认 UA（python-urllib） |
| `HTTP 400: MissingSessionID` | 必须带 `x-opencode-session` |

**结论**：`LLM_USER_AGENT` 必须非空，`LLM_SESSION_HEADER=x-opencode-session`，值进程内自动生成。

**什么时候该推翻**：换到 DeepSeek/通义/本地 vLLM 时，这两个头不需要，留空即可。

## ADR-006 · 合并策略用 fill_only（模型只补空）

**日期**：2026-11-01 ｜ **状态**：生效

**背景**：规则和模型都抽字段，谁覆盖谁？

**实测**（28 份样本，claude-haiku）

| 策略 | 留出集 | 调优集 |
|---|---|---|
| **fill_only（模型只补空）** | **98.7%** | **98.7%** |
| floor 0.8 / 0.7 / 0.6 | 97.4% | 98.7% |
| **llm_wins（模型优先，最初的实现）** | 97.4% | **95.0%** |

单看：模型 92.2%，规则 97.4%。

**结论**：`MERGE_POLICY=fill_only`。**不让模型污染已经正确的值。**

**复现**：`MERGE_POLICY=llm_wins make eval` 对比。

**什么时候该推翻**：真实客户数据上规则明显变弱（比如准确率 <85%）时，应重新做这组实验。

## ADR-007 · 按需调用模型（LLM_STRATEGY=auto）

**日期**：2026-11-01 ｜ **状态**：生效

**背景**：模型单条 5 秒，现场演示会冷场。

**结论**：规则已覆盖必填且置信度 ≥0.6 时不调模型。

| 场景 | 行为 | 实测 |
|---|---|---|
| 结构化托书 | 跳过模型 | 18ms |
| 口语/改单 | 调模型 | ~5s |
| 重复评测 | 命中缓存 | 30ms |

**代价**：约 1pp 精度（97.4% vs 98.7%）。**收益：快 100 倍。**

**复现**：`LLM_STRATEGY=always make eval` 对比。

## ADR-008 · 分级审批按"风险字段"判，不按全字段

**日期**：2026-11-01 ｜ **状态**：生效

**背景**：第一版按"所有字段置信度 ≥95%"判自动通过，结果 **auto 永远是 0**——备注、品名这类选填项本来就不确定。

**结论**：只看**高代价字段**——箱号 / 箱型 / 箱量 / 截港 / 电话，全部 ≥0.90 且无提醒才直过。

**依据**：这些字段错了要被码头退回、误船、重派车，是罚款来源；地址错了最多返工一次。

**一句话话术**：**"自动通过不是说全对，是说会罚钱的字段都对。"**

## ADR-009 · 多版本 OCR 用规则裁决 + 保守切换

**日期**：2026-11-01 ｜ **状态**：生效（效果有限）

**背景**：图像模糊时有多种增强方案，选哪个当结果？

**走过的弯路**

1. 按"字数多少"选 → 选到更长但更错的版本
2. 按"平均置信度"选 → 同上
3. 按"领域规则得分"选（能否抽出合法箱号/可解析时间） → 好一些
4. 再加**保守切换**：除非增强版规则得分高出 2 分以上，否则用原图

**实测结果**

| 退化程度 | 关闭增强 | 开启增强 |
|---|---|---|
| 轻 | 5/5 | 5/5 |
| 中 | 2/5 | 2/5（改 D14 后 3/5） |
| 重 | 0/5 | 0/5 |

**结论**：保留多版本机制（保证不比单跑差），但**不要指望图像增强能救坏图**——真正瓶颈是字段名误识（见 ADR-010）。

## ADR-010 · 字段名容错 = 相似度 + 值形态双重判定

**日期**：2026-11-01 ｜ **状态**：生效

**背景**：OCR 把"箱号"认成"第号"、"截港"认成"藏港"，值识别对了但抽不出来。

**关键难点**：`箱号` 和 `封号` 只差一个字，`截港` 和 `截关` 也是。**只比相似度会把它们混起来。**

**结论**：两个条件同时满足才认——标签相似度 ≥0.6 **且** 值通过该字段的形态校验（箱号过 ISO 6346 / 时间能解析 / 电话像电话）。

单字标签（`号：SL8823101`）再用**值形态特异性**打分区分：纯字母数字短串 → 封号（2.5），带连字符/含多位数字 → 单号（1.0）。

**效果**：中档退化 2/5 → 3/5；干净集**零假阳性**。

**明确不做**：数字级误识（少一位、错一位）修不了，只能靠置信度提示 + 人工兜底。

## ADR-011 · 风险模拟必须做 Laplace 平滑

**日期**：2026-11-01 ｜ **状态**：生效（**最重要的一条**）

**背景**：模拟演练中，12 单自动通过、0 单被改，风险模拟直接输出：

> **"数据支持取消大部分人工确认"**

**问题**：这是拿 12 个样本赌全年 2,000 单。

**结论**：错单率用 `(错单+1)/(样本+2)`，而不是 `错单/样本`。

| | 错单率 | 月损失 | 结论 |
|---|---|---|---|
| 平滑前 | 0% | 0 元 | 支持取消 ❌ |
| 平滑后 | 7% | 790,476 元 | 不建议取消 ✅ |

**一句话**：**系统不能因为"没见过错"就说"不会错"。**

## ADR-012 · 修正率的分母 = 已确认单的全部非空字段

**日期**：2026-11-01 ｜ **状态**：生效

**背景**：第一版分母写成"被改过的字段数"，分子也是它 → **永远 100%**。

**影响**：客户第一眼会认为"系统全错"，直接否掉。

**结论**：分母 = 已确认单的非空字段总数。实测从 100% 变为 **0.4%**。

## ADR-013 · 弱金标 + 抽检校准

**日期**：2026-11-01 ｜ **状态**：生效

**背景**：客户没有人工标注的答案，只有 TMS 里当年的录入结果；而 TMS 本身有错。

**结论**：把 TMS 当弱金标先算一个原始准确率，再抽 10% 的"不一致单"人工判谁错，用比例反推真实水平，并给 95% 置信区间（Wilson）。

**效果**：原始 99.0% → 校正 100%，CI 87.9%–100%。

**注意**：抽检量小的时候区间很宽，**要照实说，不能只报点估计**。

## ADR-014 · 幂等用内容比对，不用请求去重

**日期**：2026-11-01 ｜ **状态**：生效

**背景**：两个人同时点确认怎么办？

**选项**

| 方案 | 问题 |
|---|---|
| A. 按请求 ID 去重 | 两个人各自的请求 ID 不同，都会执行 |
| B. 内容比对 | 内容相同 → 幂等；内容不同 → 409 |

**结论**：B。因为"内容不同"往往意味着**真的有人改了东西**，不能静默丢弃。

## ADR-015 · 改单多候选不猜

**日期**：2026-11-01 ｜ **状态**：生效

**背景**：客户改单没写原单号，只能按"箱号 / 客户 + 近 3 天"反查。

**结论**：匹配到**唯一**候选才自动套用；多个候选**返回列表让人选**。

**依据**：改错单比不改更糟——会把 A 单的变更套到 B 单上。

## ADR-016 · 明确不做的事

**日期**：2026-11-01 ｜ **状态**：生效

| 不做 | 理由 |
|---|---|
| 智能调度 / 配载优化 | 依赖货源池与司机意愿，不是算法问题 |
| TMS / 财务软件对接 | 本阶段不做；接口风险会把 3 周拖成 3 个月，客户给文档后按 C2 单独评估 |
| 多租户 | 单租户客户交付，多客户按实例部署；决定做 SaaS 前不补 |
| 工具库 / 插件 / 低代码 | 只有 2 个应用，抽象一定错 |
| 企微 AES 加密模式 | 需接官方加解密库，上生产前必须补 |
| 图像透视矫正 / 去水印 / 超分 | 属于文档检测范畴，当前 ROI 不划算 |
| 数字级 OCR 纠错 | 修不了，交给置信度 + 人工 |

> 2026-11-02 更新：登录与四角色（A1 / A2）已解禁并落地，理由见 CHANGELOG 0.17.0；
> 2026-11-08 更新：TMS 写回列为 C2，需客户接口文档后单独评估；多租户仍不在范围内，客户隔离靠“一客一实例”。

**规则**：这份清单里的任何一项要解禁，必须先改本文档并说明理由。

## ADR-017 · 催收话术：模型只润色，数字由规则锁定

**日期**：2026-11-08 ｜ **状态**：生效

**背景**：催收话术需要自然、可读，但金额、逾期天数、客户名不能出错；模型直接生成容易改数字或加法律威胁。

**结论**：
- 默认使用分档模板 + 占位符，数字由规则注入。
- 可选的 `aging.ai_draft` 只让模型改写措辞；输出必须通过客户名/金额/天数/数字范围校验。
- 不合规、模型不可用、未配置模型 → 回退模板；只提供人工核对后的复制，不自动发送。
- 默认关闭，避免每次分析产生 token 成本。

**依据**：财务话术的准确性优先于语言多样性；不能为了“像 AI”把可审计的数字交给模型。

## ADR-018 · TMS 写回：固定契约，客户侧做映射

**日期**：2026-11-08 ｜ **状态**：生效

**背景**：每家 TMS 的字段名、鉴权、错误码都不同；在拿到客户接口文档前，按某一家猜一套字段，等于写死一个错误契约。

**结论**：
- ai-copilot 只发一份固定契约 JSON（`schema=ai-copilot/tms-generic-v1`），字段为 `booking.*`。
- 客户在自己的 TMS 侧或中间适配器里做字段映射。
- 发件箱 + 幂等键（`run_id+version`）+ 重试；2xx 成功、4xx 永久失败、5xx/网络重试。
- 未拿到真实文档前，不声称“已对接某家 TMS”；mock 只证明协议与重试。

**依据**：接口契约是客户资产，不能靠猜；通用层能先跑通可靠性，真实映射只是最后一层薄适配。
