# 行业包设计：先验证深度，再复制宽度

> 版本：v0.4 ｜ 日期：2026-11-20 ｜ 状态：**Step 3 完成（买方运费审计 dry-run 已跑通）**
> 关联：`packs/README.md`、`docs/AI需求实施计划.md`、`会客包/23_协丰与同类企业AI需求地图.md`
> 边界：本文是内部研发文档，不对外；不把规则/脚本包装成大模型。

---

## 1. 为什么现在做这件事

当前 `ai-copilot` 的能力已经很宽：34 个页面、191 个端点，覆盖单证、对账、账龄、
结算、报价、在途、调度、预测、关务、知识库、成本毛利、经营洞察、驾驶舱。

但证据很窄：真实客户样本 0、真实 POC 0、真实 TMS 0、真实经营数据 0。

继续横向扩行业，会把“未验证的宽度”再乘一遍；继续纵向堆功能，会把“未验证的深度”
再堆一层。两者都不解决“证据”问题。

所以方向是：

> **先用一个楔子拿到真实数据和价值账，再把验证过的东西抽成行业包复制。**

行业包不是为了“配置化”本身，而是为了回答：

> 进一个新行业，能不能不改内核，只换字段、口径、样例和验收指标？

---

## 2. 两层结构

| 层 | 内容 | 变化频率 | 谁维护 |
|---|---|---|---|
| **领域内核** | OCR、模型网关、字段抽取、置信度、人工确认、规则调度、单据匹配、差异解释、账龄、成本、洞察、审计、权限、部署 | 低 | 研发 |
| **行业包** | 字段字典、校验参数、对账口径、账龄/费用/成本词表、地域词表、样例、验收指标 | 高 | 交付 + 研发 |

一个行业包 = **配置 + 20–50 份样例 + 一套验收脚本**。不改内核。

---

## 3. 文件格式

采用 JSON，理由：零依赖、与现有 `data/settings.json` 一致、导入导出简单。
不引入 YAML，避免多一套解析依赖。

```text
packs/<pack_id>/
  pack.json          # id / name / version / documents / settings_refs
  fields.json        # booking / invoice 字段
  rules.json         # validations + review
  reconcile.json     # statement / match / statuses
  aging.json         # 账龄表头同义词
  fees.json          # 费用表头 + 内置费用名
  cost.json          # 毛利收入/成本表头同义词
  geo.json           # 城市/区县/港区/错别字/镇街
  acceptance.json    # 验收目标 + 最小样本量
```

字段只声明“用哪种内置归一化器”，不写任意代码：

```text
text | number | amount | datetime | container_list | container_type | so_no | alnum_upper
```

校验只允许固定类型：

```text
builtin.required | builtin.iso6346 | builtin.qty_match | builtin.enum
builtin.regex | builtin.geo | builtin.deadline | builtin.ordering
```

## 4. 代码怎么接（Step 1 已实现）

### 4.1 拆纯数据模型，避免循环依赖

```text
app/domain.py     # FieldSpec / ValidationSpec / Check / Draft / FieldValue
app/pack.py       # load_pack / validate_pack / active_pack
app/schema.py     # 兼容层：SPECS = active_pack().documents["booking"]
```

`schema.py` 对外接口保持不变，所有 `from .schema import FIELD_KEYS` 的下游代码零改动。

### 4.2 `rules.py` 改为遍历校验定义

```python
VALIDATORS = {
    "builtin.required": _required,
    "builtin.iso6346": _iso6346,
    "builtin.qty_match": _qty_match,
    "builtin.enum": _enum,
    "builtin.regex": _regex,
    "builtin.geo": _geo,
    "builtin.deadline": _deadline,
    "builtin.ordering": _ordering,
}

def run_checks(draft, now=None):
    checks = []
    for rule in active_pack().validations:
        if not _enabled(rule):
            continue
        checks.extend(VALIDATORS[rule["type"]](draft, rule, now))
    return checks
```

ISO 6346、时间解析、匹配状态机等算法一行不改。

### 4.3 `reconcile.py` 只把词表换成参数

`parse_statement(text, spec)`、`reconcile(..., spec)`；匹配算法、双向比对、CSV 导出不动。

### 4.4 可追溯

`Draft` 增加 `pack_id` / `pack_version`，每次解析落库。客户问“这个结果当时是什么
口径算的”，能答出来。

### 4.5 实际落地文件

| 文件 | 作用 |
|---|---|
| `app/domain.py` | `FieldSpec` / `ValidationSpec` / `Pack` / `Draft` 等纯数据模型；字段类型、归一化器、校验器固定枚举 |
| `app/pack.py` | `load_pack` / `active_pack` / `reload_pack`；只加载 JSON，不执行任意代码 |
| `app/schema.py` | 兼容层：`SPECS` / `FIELD_KEYS` / `LABELS` / `SPEC_MAP` / `BLOCKING_KEYS` 从 pack 派生，下游 import 不变 |
| `app/invoice.py` | 发票字段从 `pack.documents["invoice"]` 派生 |
| `app/rules.py` | 遍历 `pack.validations`，按固定校验器分派；算法、ISO 6346、时间解析不动 |
| `app/extract.py` | `_stamp()` 写入 `pack_id` / `pack_version` |
| `app/reconcile.py` | 表头同义词、匹配键、multi 键、金额字段、状态文案、展示字段从 `pack.reconcile` 派生；匹配/双向比对算法不动 |
| `app/statement.py` | 明细列同义词 `line_hints` 与 `line_map` 读 pack；文本对账单 API 可跑第二包 |
| `app/aging.py` | 账龄表头同义词从 `pack.aging` 派生；分档与话术仍在 settings |
| `app/fees.py` | 费用表头与内置费用名从 `pack.fees` 派生；现场补充仍走 `data/fee_dict.txt` |
| `app/settlement.py` | 外协结算的费率/报账表头从 `pack.fees.settlement` 派生 |
| `app/margin.py` | 毛利收入/成本表头从 `pack.cost` 派生 |
| `app/address_check.py` | 城市/区县/港区/错别字/镇街词表从 `pack.geo` 派生 |

## 5. 与 `settings.json` 的边界

| 放 pack | 放 settings |
|---|---|
| 字段、字段含义、是否必填 | 必填项勾选 |
| 校验类型与参数 | 校验开关 |
| 对账表头/匹配键/金额字段 | 金额容差 |
| 账龄/费用/成本词表 | 分档天数、毛利预警线 |
| 验收目标 | 催收话术模板 |

> 改了会改变“字段含义/报告口径” → pack；只是松紧、开关、文案 → settings。

## 6. 加载、优先级与回滚

```text
代码内置默认
  → packs/<PACK_ID>/                  # 行业包
  → data/packs/<PACK_ID>/local.json   # 现场覆盖，不进 git
  → data/settings.json                # 运行参数
```

- `PACK_ID` 环境变量，默认 `trucking`；
- pack 加载失败 → 回退内置默认并告警，不让客户系统起不来；
- 版本化目录 + 激活指针；`POST /api/packs/activate` 切换并审计；
- 回滚 = 切指针，和现有 settings 历史/回滚同一套思路。

### 7.6 Step 3：第二行业包 dry-run（已完成）

新建 `packs/freight_audit/`（买方运费审计），目标不是交付，而是证明：

> 同一套 `app/` 内核，不改一行代码，只换 pack，就能跑另一套字段、校验和对账口径。

包内容：

| 文件 | 内容 |
|---|---|
| `fields.json` | 审计行 10 个字段（承运商/账单号/运单号/费用代码/账单金额/合同价/差异/争议状态等）+ 承运商发票 15 个字段 |
| `rules.json` | 必填 / 低置信 / 金额格式 / 合同价格式；不跑箱号、截港、地址规则 |
| `reconcile.json` | 账单号 → 运单号 → 费用代码；账单金额 vs 合同价；展示“账单号/运单号” |
| `acceptance.json` | 字段准确率 90%、修正 ≤60 秒、差异召回 ≥95%、误报 ≤10% |
| `aging/fees/cost/geo` | **不提供**：本包不使用这些领域，加载器按空字典处理 |

同时做了两件必要的适配：

1. `app/pack.py` 支持**部分 pack**：核心 4 个文件必需，领域文件可选。
2. `app/statement.py` 的明细列同义词和 `to_reconcile_rows` 改为读
   `pack.reconcile.statement.line_hints` / `line_map`；文本对账单 API 也能跑第二包。

复现命令与结果：

```bash
cd ai-copilot

```

`packdiff` 的关键结论：

- 字段：托书 20 个 → 审计行 10 个；发票 15 个字段保留，仅标签按买方口径调整；
- 校验：去掉 7 条集卡规则（箱号/箱量/箱型/封号/电话/地址/截港），增加 2 条金额格式规则；
- 对账：匹配键从“运单号 → 箱号”改为“账单号 → 运单号 → 费用代码”，金额侧从 `freight` 改为 `contract_rate`；
- 验收：修正秒数 90 → 60，差异召回 90% → 95%；
- 可选领域：`aging/fees/cost/geo` 在 freight_audit 中不存在。

API 级验证（`PACK_ID=freight_audit` 启动临时实例）：

- `/api/health` 200；
- `/api/meta` 返回 `carrier / carrier_invoice_no / shipment_no / charge_code / amount`；
- `POST /api/reconcile` 文本对账单：`账单号,运单号,费用代码,账单金额` + 合同价 1000
  → `amount_diff`，差异 200。

回归（默认 `trucking`）：

- `make pack-lint` / `pack-snapshot` / `pack-test`（34 项）全过；
- `smoke.sh` 19/19；
- `LLM_PROVIDER=rule make eval` exit 0，结果与 Step 2 相同；
- `/api/reconcile` 集卡文本路径仍为 `ok=1`，行为未变。

边界（必须写清）：

- `freight_audit` 是**合成 dry-run**，没有真实客户账单样本，不能当真实准确率；
- 文本层的 `charge_code` 暂映射到 `remark`（StatementDocument 还没有独立 `charge_code` 字段）；
  正式接入应在 statement schema 增加该字段；
- OCR 行兜底 `_ocr_rows` 仍是集卡形状（运单号/箱号正则），本 dry-run 未使用；
- 没有专门的审计 UI 页面；页面会按 pack 字段渲染，但买方审计工作流仍需产品化。
