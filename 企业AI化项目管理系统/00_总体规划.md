# 企业AI化项目管理系统 · 总体规划

> 版本 v0.1 ｜ 定位：产品规划与系统设计基线

---

## 1. 定位判断

### 1.1 它不是通用项目管理工具

Jira / 飞书项目 / 禅道回答三个问题：**谁做、什么时候做完、卡在哪**。

但企业 AI 化项目真正的失败原因，几乎从来不是"延期"：

| 真实失败原因 | 表现 |
|---|---|
| 价值假设没验证就开发 | 做了三个月，发现业务根本不需要 |
| 数据拿不到却先写代码 | 模型精度上不去，归因于"数据质量" |
| 客户老板不知道钱花在哪 | 二期预算批不下来 |
| 上线后没人用、没人算账 | 交付即终点，无 ROI 证明 |

所以本系统要回答的是另外三个问题：

1. **这件事值不值得做？** —— 价值假设 + 证据
2. **我们凭什么相信能做成？** —— 数据 / 技术 / 组织可行性
3. **做成了没有？** —— 基线 → 目标 → 实测

> **通用 PM 管"任务"，本系统管"判断"。**

### 1.2 一句话定位

> 把企业 AI 化交付方法论固化成软件：以"AI 机会点"为主线，以"价值假设"为证据，串起 **诊断 → 方案 → POC → 交付 → 运营** 的完整链路，并向客户侧输出他们能看懂、能拍板、能交差的信息。

### 1.3 三个不可替代的价值

| 价值 | 说明 | 对谁有用 |
|---|---|---|
| **方法论沉淀** | 每个行业一套诊断模板、访谈提纲、机会库、ROI 模型 | 供应商：新人 3 天上手 |
| **证据链** | 每个结论都可追溯到访谈记录、数据、假设验证结果 | 客户：凭什么信你 |
| **客户可感知** | 客户随时看到进度、价值、风险，续约与复购率提升 | 供应商：生意 |

## 2. 核心设计原则

| # | 原则 | 展开 |
|---|---|---|
| **P1** | **假设先行，任务在后** | 先登记"我们假设订单解析准确率能到 95%"，再拆任务去验证。任务不能凭空产生 |
| **P2** | **基线不立，方案不写** | 任何 ROI 必须有基线值 + 数据来源 + 采集日期，否则标记为"未验证假设" |
| **P3** | **客户侧不做项目管理** | 客户只做三件事：**知情、决策、配合**。绝不让客户学一套系统 |
| **P4** | **一个机会点一条命** | 每个 AI 机会点独立走生命周期，可暂停、可终止，终止必须记录原因 |
| **P5** | **交付物自动生成** | 报告、PPT、PRD、接口清单从结构化数据生成，而不是另开文档重写 |
| **P6** | **轻量寄生，不抢地盘** | 上层管"为什么做/值不值"，下层任务同步到客户已有的 Jira/飞书 |

## 3. 角色与双端设计

### 3.1 供应商侧（内部工作台，功能可以很重）

| 角色 | 核心诉求 | 系统要给他的 |
|---|---|---|
| 销售 / BD | 这个客户值不值得投入售前 | 客户画像、机会地图初稿、预估合同额 |
| 项目总监 | 多个项目健康度 | 组合看板、风险预警、资源冲突 |
| 项目经理（PM） | 进度、交付物、客户满意度 | 阶段看板、门禁清单、客户反馈 |
| **诊断顾问** | 快速摸清客户现状 | 访谈提纲、盘点表、机会库、自动生成诊断报告 |
| **产品负责人** | 需求是否清晰、范围是否可控 | 需求池、PRD 生成、验收标准、变更记录 |
| **技术负责人** | 数据能不能拿到、集成风险 | 系统盘点、接口清单、架构方案、技术可行性评分 |
| 交付 / 实施 | 上线不翻车 | 实施清单、UAT 用例、上线检查表 |
| 客户成功 | 价值是否兑现、能否续约 | 价值追踪看板、续约提醒 |

### 3.2 客户侧（协作门户，必须极轻）

| 角色 | 核心诉求 | 系统要给他的 |
|---|---|---|
| **决策人**（老板/总经理） | 花多少钱、多久见效、风险多大 | 一页纸简报、ROI 结论、待拍板事项 |
| **项目负责人**（内部 owner） | 我要协调谁、给什么、推到哪一步 | 任务清单、资料清单、进度同步、风险提醒 |
| **业务负责人**（如调度经理） | 我的业务会不会被打乱 | 业务流程图确认、验收标准、试点范围 |
| **IT / 数据负责人** | 安全、对接、数据出不出得去 | 接口清单、数据安全方案、部署架构 |

### 3.3 双端关系

```
供应商内部工作台（重）  ←──共享同一份数据──→  客户协作门户（轻）
   · 完整方法论                        · 只读进度
   · 全部假设与证据                    · 待办与待批
   · 内部成本与毛利                    · 不给看内部成本
   · 交付物编辑                        · 交付物确认/下载
```

**关键约束：客户门户永远不暴露供应商的内部成本、毛利、人员分配和内部争论。** 这是双端权限模型的第一原则。

## 5. 核心对象模型

### 5.1 主线：Opportunity（AI 机会点）

整个系统围绕一个对象展开。**Opportunity 是本系统的"项目"**。

```
Client ──< Engagement ──< Opportunity ──< Hypothesis
                              │              │
                              ├──< Baseline   └──< Validation
                              ├──< Solution
                              ├──< POC
                              ├──< Deliverable
                              └──< ValueRecord
```

| 实体 | 说明 |
|---|---|
| **Client** | 客户企业与组织架构 |
| **Stakeholder** | 干系人（姓名/角色/影响力/态度/关注点） |
| **Engagement** | 一次合作（可以是诊断合同、也可以是全周期） |
| **Opportunity** | 一个可独立评估、独立交付的 AI 应用点 |
| **Hypothesis** | 支撑该机会点的价值/可行性假设，**必须被验证或推翻** |
| **Baseline** | 基线指标（值 + 数据来源 + 采集日期 + 采集人） |
| **Solution** | 方案（技术路线、集成、工作量） |
| **POC** | 验证实验（样本、方法、指标、结论） |
| **Deliverable** | 交付物（模板实例化） |
| **ValueRecord** | 上线后的实测价值 |

### 5.2 Opportunity 状态机

```
候选 Candidate
   ↓ 打分
已评估 Scored
   ↓ 客户/内部选中
已选 Selected
   ↓
方案设计 Designed
   ↓
POC 中 Piloting ──→ POC 失败 → 终止 Killed（记录原因）
   ↓ 通过
已验证 Validated
   ↓
交付中 Delivering
   ↓
已上线 Live
   ↓
价值达成 Realized
   ↓
关闭 Closed
```

旁路状态：`Parked`（搁置，等待数据/预算/时机）、`Merged`（合并到其他机会点）。

**强制规则：任何进入 `Killed` 的机会点必须填写"终止原因 + 证据"。** 这些被否掉的机会点恰恰是最有价值的资产——它防止下一个项目重复踩坑。

## 6. 阶段与门禁

| 阶段 | 名称 | 目标 | 出口门禁 | 典型周期 |
|---|---|---|---|---|
| S0 | 商机与售前 | 判断值不值得投入 | G0 立项门禁 | 1–2 周 |
| **S1** | **诊断调研** | **摸清现状、识别机会、算清账** | **G1 诊断门禁** | **2–3 周** |
| S2 | 方案设计 | 形成可交付方案与报价 | G2 方案门禁 | 2–4 周 |
| S3 | POC 验证 | 用真实数据证明可行 | G3 验证门禁 | 4–8 周 |
| S4 | 交付实施 | 上线并被真实使用 | G4 上线门禁 | 8–16 周 |
| S5 | 运营与价值 | 兑现 ROI、发现二期 | G5 价值门禁 | 持续 |

**门禁不是流程审批，而是"证据检查"。** 每个 Gate 有明确的检查清单，缺一项就打回。这是本系统与通用 PM 最大的流程差异。

## 7. 客户门户设计原则

| 原则 | 说明 |
|---|---|
| **不新增学习成本** | 不要求客户登录复杂系统；关键信息通过企业微信/邮件推送 |
| **一屏三件事** | 进度、待办、待批。其他都折叠 |
| **每阶段一页纸** | 诊断一页纸、方案一页纸、POC 结论一页纸、上线一页纸 |
| **只读为主** | 客户能填的只有：资料上传、确认/驳回、评分反馈 |
| **可留痕** | 客户每一次确认和驳回都形成决策记录，避免后期扯皮 |
| **数据隔离** | 客户只能看自己项目；供应商内部成本不可见 |

## 8. 与现有工具的关系

| 工具 | 关系 |
|---|---|
| Jira / 飞书项目 | **下游**。任务级执行在那边，本系统只同步里程碑状态 |
| 企业微信 / 钉钉 | **入口**。客户门户和内部提醒寄生于此 |
| 飞书文档 / Notion | **可替代**。交付物由系统生成，不必再手工维护 |
| CRM（如销售易） | **上游**。商机与合同从 CRM 同步 |
| 数据平台 | **对接**。基线数据与实测指标从客户数据平台取数 |

> 定位：**做上层，不做底层。** 与所有工具都是"同步"关系，不要求替代。

## 9. 迭代路线

### MVP（第 1 期，6–8 周）：只做调研阶段

**目标：让诊断顾问的效率翻倍，并直接产出客户能拍板的报告。**

| 范围 | 内容 |
|---|---|
| ✅ 做 | 客户档案、干系人、访谈记录、四维盘点、痛点库、机会地图、ROI 计算器、诊断报告自动生成、客户只读门户 |
| ❌ 不做 | POC 管理、交付实施、运营追踪、计费 |

**为什么先做这一段：**
1. 调研是所有项目的入口，复用率最高
2. 调研的产出物最标准，最容易模板化
3. 顾问的时间最贵，效率提升最直观
4. 不依赖客户系统对接，落地阻力最小

### 第 2 期：方案 + POC
机会点 → 方案 → 实验设计 → 验证结论。

### 第 3 期：交付 + 运营
实施管理、价值追踪、续约。

### 第 4 期：知识库 + AI 助手
行业机会库、相似项目推荐、访谈自动摘要。

## 10. 技术架构建议

| 层 | 建议 | 理由 |
|---|---|---|
| 前端 | Next.js + Tailwind | 双端（内部工作台 + 客户门户）同一代码库，按角色渲染 |
| 后端 | Node/NestJS 或 Python(FastAPI) | 后期要做 AI 能力，Python 生态更顺 |
| 数据库 | PostgreSQL | 结构化强，JSONB 存灵活字段（盘点表、评分） |
| 对象存储 | S3 兼容 | 访谈录音、客户资料、生成的报告 |
| LLM | 可切换（国产 + 海外） | 客户数据敏感性要求可切私有化 |
| 部署 | 多租户 SaaS 优先 | 供应商自己用，客户侧轻量接入 |
| 权限 | RBAC + 项目级数据隔离 | 客户只能看自己项目 |

**一个必须提前做的决定：** 客户资料里包含报关、客户名单等敏感信息，**LLM 调用必须支持"不出境 + 可脱敏"**，否则大客户过不了安全评审。

## 11. 系统自身的成功指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 诊断到签约转化率 | 完成诊断的客户中签约比例 | 提升 20% |
| 诊断周期 | 从 kickoff 到 G1 通过 | ≤ 3 周 |
| 交付物生成率 | 由系统生成而非手写的交付物占比 | ≥ 80% |
| 机会点命中率 | 诊断推荐且最终落地的机会点占比 | ≥ 50% |
| 客户满意度 | 每阶段客户评分 | ≥ 4.5/5 |
| 续约率 | 二期/续约合同占比 | ≥ 60% |
