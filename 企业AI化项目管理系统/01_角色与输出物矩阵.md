# 角色与输出物矩阵

> 这份文档回答一个问题：**每个角色在什么阶段、需要看到什么、系统怎么把它变出来。**

> **重要前提（2026-10 决策）：本期不做客户侧门户。**
> 客户侧的四个角色**不是系统用户，而是交付物的读者**。系统的职责是：把他们的诉求转换成电子文档，由顾问人工交付，并登记外发记录。
> 因此第 2 节的描述应理解为"文档设计需求"，而不是"界面设计需求"。

系统设计的最大误区，是把"客户侧"当成权限受限的内部用户。实际上客户侧的角色有完全不同的动机。

---

## 1. 角色全景

```
┌─ 供应商侧（内部工作台）──────────────┐   ┌─ 需求方侧（协作门户）──────────┐
│ 销售/BD                              │   │ 决策人（老板/总经理）           │
│ 项目总监                             │   │ 项目负责人（内部 owner）        │
│ 项目经理 PM                          │   │ 业务负责人（如调度经理）        │
│ 诊断顾问          ← 调研阶段主力      │   │ IT/数据负责人                  │
│ 产品负责人                            │   │                                │
│ 技术负责人                            │   │                                │
│ 交付/实施                             │   │                                │
│ 客户成功                             │   │                                │
└──────────────────────────────────────┘   └────────────────────────────────┘
```

**关键：两侧看的不是同一份东西。** 内部看全量假设、成本、风险；客户看结论、决策、自己的待办。

---

## 2. 客户侧四个角色深度拆解

### 2.1 决策人（老板 / 总经理 / 分管副总）

**他的处境：** 一年被无数供应商"数字化/智能化"方案轰炸，听过太多"AI 能降本 30%"。他不缺方案，缺的是**判断依据**。

**他最怕的三件事：**
1. 钱花了没效果，还没人负责
2. 项目变成 IT 部门和供应商的"技术自嗨"
3. 内部推不动，最后自己背锅

**他真正要的：**
- **一句话结论**：这事值不值、要多少钱、多久见效
- **可对赌的数字**：不是"提升效率"，而是"单证岗从 5 人降到 2 人，或者不增人接 30% 更多单"
- **退出机制**：做到哪一步可以停

**系统给他什么：**

| 输出物 | 时机 | 形式 |
|---|---|---|
| 一页纸诊断简报 | G1 门禁 | 1 页 PDF / 微信图文，3 分钟读完 |
| 投入产出表 | G1 / G2 | 一张表：投入、收益、回本周期、置信度 |
| 风险与退出条件 | G2 | 3 条以内，明确"什么情况下建议停" |
| 月度/阶段进展 | 每阶段末 | 半页，只讲"做成了什么、还差什么、要不要你拍板" |

> **设计要点：决策人永远不需要登录系统。** 所有给他的内容必须能通过微信直接打开，且不需要账号。需要他确认的，用"回复 1 同意 / 2 驳回"级别的交互。

---

### 2.2 项目负责人（客户内部 owner，通常是副总/信息化负责人/运营总监）

**他的处境：** 他是这件事在客户内部的"担保人"。项目成了是他的功劳，砸了是他的责任。但他往往**没有强权**，只能靠协调。

**他最怕的三件事：**
1. 老板问"进展怎么样"，他答不上来具体数字
2. 各业务部门不配合，他推不动
3. 供应商交付延期，锅算他的

**他真正要的：**
- **汇报素材**：能直接拿去开会的材料（这是他最刚需的）
- **协调抓手**：明确"这件事需要谁、什么时候、给什么"，可以转发给对应部门
- **风险预警**：提前知道哪里要出问题，好提前铺垫
- **功劳归属**：项目成功后，有数据证明是他的推动带来的

**系统给他什么：**

| 输出物 | 时机 | 形式 |
|---|---|---|
| 阶段汇报包（PPT/Word） | 每阶段末 | 可直接投屏，含数据、图表、结论 |
| 内部协调清单 | 每阶段初 | "需要 XX 部门提供 XX 资料，截止 X 月 X 日"，可一键转发 |
| 干系人关注点提示 | 全程 | "IT 负责人关心数据出境，建议提前沟通" |
| 风险预警 | 实时 | 提前 3–5 天推送 |
| 价值实现报告 | S5 | 年终总结素材，量化"我们做成了什么" |

> **这是整个产品最重要的杠杆：**
> **帮客户的项目负责人"完成他的内部政治任务"，他就会成为你在客户内部的销售。**
> 反过来，如果系统只给他一个进度条，他不但不用，还会觉得你在增加他的工作量。

---

### 2.3 业务负责人（如调度经理、单证主管、仓储主管）

**他的处境：** 他是被"AI 化"的对象。他的第一反应往往是防御：**"AI 是不是要替代我？"**

**他最怕的三件事：**
1. 系统上线后自己不会用、被边缘化
2. 现有流程被打乱，出了事算他的
3. 被要求额外填表、额外配合，纯增加负担

**他真正要的：**
- 被尊重：他的经验被写进方案，而不是被"算法替代"
- 边界清晰：试点范围多大、什么时候轮到我
- 减负证明：先让我看到"这事能让我少加班"

**系统给他什么：**

| 输出物 | 时机 | 形式 |
|---|---|---|
| 现状流程图（他确认版） | S1 | 打印出来逐条对，让他签字确认 |
| 痛点确认清单 | S1 | 他说过的痛点，原话记录 |
| 试点范围说明 | S2/S3 | 明确"只影响 X 环节，不影响 Y" |
| 验收标准 | S2 | 由他参与制定，而不是被通知 |

> **设计要点：诊断阶段的访谈记录必须对业务负责人可见并确认。** 这一步做好了，后面推行阻力小一半。

---

### 2.4 IT / 数据负责人

**他的处境：** 所有外部系统都要过他这一关。他的 KPI 里没有"帮供应商成功"，只有"不出安全事故"。

**他最怕的三件事：**
1. 数据出境 / 数据泄露，责任在他
2. 供应商要一堆接口，他的团队配合不过来
3. 上线后系统不稳定，故障算他的

**他真正要的：**
- **一页纸说清楚**：数据从哪来、经过哪、存哪、谁能看
- **接口清单**：要什么字段、什么频率、谁提供
- **最少的改动**：能用现有接口就别新建

**系统给他什么：**

| 输出物 | 时机 | 形式 |
|---|---|---|
| 数据流与安全说明 | S1/S2 | 一页图 + 一页文字 |
| 接口需求清单 | S2 | 表格：系统、接口、字段、频率、提供方 |
| 部署架构图 | S2 | 云/私有化、网络边界 |
| 权限与审计说明 | S2 | 谁能看什么、留痕方式 |

## 3. 供应商侧两个关键角色

> 说明：这里的"产品/技术负责人"按**供应商侧**理解。若客户侧也有对应的产品或 IT 负责人，其诉求见 2.4，差异在于：**客户侧要"少改动 + 安全"，供应商侧要"范围可控 + 风险早暴露"**。

### 3.1 产品负责人

**他的处境：** 夹在销售（什么都能答应）和交付（做不完）之间。AI 项目最典型的事故是**范围蔓延**——客户一句"顺便再加个功能"，工期翻倍。

**他最怕的三件事：**
1. 需求边界不清，验收扯皮
2. 客户口头承诺的东西没有留痕
3. 做到一半发现核心假设不成立

**他真正要的：**
- **需求的可追溯性**：每条需求对应哪个机会点、哪个假设、哪次访谈
- **范围边界的证据**：不是"我们说好了"，而是"白纸黑字 + 客户确认记录"
- **变更影响评估**：加这个功能，工期和成本变多少

**系统给他什么：**

| 输出物 | 时机 | 形式 |
|---|---|---|
| 机会点 → 需求映射表 | S2 | 一张表，可追溯 |
| PRD 骨架（自动生成） | S2 | 从访谈和盘点数据生成 60%，人工补 40% |
| 范围说明书 + 客户确认记录 | G2 | 带时间戳的确认快照 |
| 变更影响评估 | 全程 | 工时/成本/风险三列 |

### 3.2 技术负责人 / 架构师

**他的处境：** 他最清楚"这事技术上能不能做"，但往往在项目后期才被拉进来，那时承诺已经许出去了。

**他最怕的三件事：**
1. 数据根本拿不到 / 质量太差
2. 客户系统老旧，集成成本失控
3. 被要求承诺一个做不到的准确率

**他真正要的：**
- **早期介入**：在报价前就知道技术风险
- **数据可行性证据**：不是"应该能拿到"，而是实际抽样看过
- **技术风险的书面记录**：出问题时能证明"我早就说过"

**系统给他什么：**

| 输出物 | 时机 | 形式 |
|---|---|---|
| 系统盘点表 | S1 | 客户有哪些系统、版本、是否有 API、谁维护 |
| 数据可得性评估 | S1 | 每个机会点标注：数据有/无/需申请/质量差 |
| 技术可行性评分 | S1 | 1–5 分，必须写理由 |
| 集成风险清单 | S2 | 风险 + 概率 + 影响 + 应对 |
| 架构方案 | S2 | 标准模板，含部署、安全、扩展性 |

> **设计要点：技术负责人必须在 S1 诊断阶段就有"一票否决权"的入口。**
> 系统里应该有一个字段：**"技术阻断项"**。一旦标记，该机会点不能进入 S2，除非有人书面承担风险。这一条能救掉大量项目。

## 5. 交付物是怎么"自动生成"的

不是"AI 写一篇作文"，而是**结构化数据 → 模板 → 文档**：

```
录入层            结构化层              生成层
──────           ────────              ──────
访谈录音    →    痛点 / 事实 / 引语  →  ┐
盘点表      →    系统 / 数据 / 接口   →  ├→ 模板引擎 → Word/PPT/PDF
机会点评分  →    价值 / 可行性 / 优先级 →  ┤       ↑
ROI 计算    →    投入 / 收益 / 回本     →  ┘   行业模板库
```

**关键设计：每个结论字段都必须有"来源"字段。**
- 这个痛点来自哪次访谈的第几分钟
- 这个数字来自客户哪张表、谁提供、什么时候
- 这个评分是谁打的、理由是什么

有了来源，报告才敢给老板看；没有来源，AI 生成的报告就是"看起来很专业的胡说"。

## 6. 三个反直觉的设计结论

| # | 直觉 | 实际 |
|---|---|---|
| 1 | 客户要的是"透明的进度" | 客户项目负责人要的是**能拿去开会的汇报素材**。进度条是给 PM 看的，PPT 是给老板看的 |
| 2 | 产品负责人要的是"完整的 PRD" | 他要的是**范围边界的证据**。PRD 可以后写，边界必须在报价前定 |
| 3 | 技术负责人要的是"架构图" | 他要的是**早期说"不"的权力**。架构图是结果，阻断项才是价值 |

## 7. 权限矩阵（简版）

| 输出物类型 | 供应商内部 | 决策人 | 项目负责人 | 业务负责人 | IT 负责人 |
|---|---|---|---|---|---|
| 内部成本与毛利 | ✅ | ❌ | ❌ | ❌ | ❌ |
| 机会地图与 ROI | ✅ | ✅ | ✅ | 部分 | 部分 |
| 完整诊断报告 | ✅ | 摘要 | ✅ | 相关章节 | 相关章节 |
| 技术风险与阻断项 | ✅ | 摘要 | ✅ | ❌ | ✅ |
| 访谈原始录音 | ✅ | ❌ | ❌ | 本人访谈 | ❌ |
| 待办与决策 | ✅ | 待拍板 | 全部 | 本人相关 | 本人相关 |
| 价值实现数据 | ✅ | ✅ | ✅ | ✅ | 部分 |
