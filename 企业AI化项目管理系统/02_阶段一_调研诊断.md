# 阶段一 · 诊断调研（S1）详细设计

> 这是 MVP 的全部范围。读完这份文档，产品、技术、顾问三方应该能对齐"调研阶段到底做什么、产出什么、怎么算过关"。

---

## 1. 阶段定义

| 项 | 内容 |
|---|---|
| **一句话目标** | 用 2–3 周摸清客户现状，识别出 3–5 个可落地的 AI 机会点，并给出"先做哪个、值多少钱、有什么风险"的结论 |
| **在做什么** | 理解业务、盘点数据、评估可行性、算 ROI、排优先级 |
| **不在做什么** | ❌ 不写技术方案 ❌ 不做原型 ❌ 不报价细项 ❌ 不做需求规格 |
| **成功标准** | 客户决策人能基于产出物做出"是否立项、先做哪个"的决定 |
| **失败信号** | 报告很厚但没有结论；机会点很多但没有排序；ROI 全是"预计"没有基线 |

> **这个阶段唯一的交付目标：让客户老板能在 10 分钟内做出一个决定。**

---

## 2. 时间盒与资源

| 项 | 建议 |
|---|---|
| 周期 | 2 周（标准）/ 3 周（多厂区、多业务线） |
| 投入 | 诊断顾问 1 名（主）+ 行业顾问 0.5 名 + 技术顾问 0.3 名 |
| 访谈 | 5–8 人，每人 45–60 分钟 |
| 现场 | 至少半天驻场观察（不可省略） |
| 数据 | 抽样 3 类：订单、车辆/作业、财务 |

**为什么必须驻场：** 客户说的流程和实际流程的差异，往往就是最大的机会点。电话访谈永远发现不了"他们其实用 Excel 在两张表之间手工对账"。

---

## 3. 四个 Step

```
S1.1 立项与对齐   2–3 天
   ↓
S1.2 现状诊断     5–8 天   ← 投入最大
   ↓
S1.3 机会识别     3–5 天   ← 价值最大
   ↓
S1.4 路线图与简报 2–3 天
   ↓
G1 诊断门禁
```

---

### S1.1 立项与对齐（2–3 天）

| 项 | 内容 |
|---|---|
| **目的** | 把"模糊的合作意向"变成"有边界的诊断任务" |
| **关键活动** | ① Kickoff 会议 ② 确定诊断范围与不做的事 ③ 干系人访谈排期 ④ 发出资料清单 |
| **输入** | 客户基本信息、初步业务描述、合同/意向书 |
| **输出** | ① 项目章程（1 页）② 干系人图谱 ③ 资料请求清单 ④ 访谈排期表 |
| **客户动作** | 指定项目负责人；确认访谈名单；安排对接人；提供资料 |
| **系统功能** | 创建 Engagement；录入 Stakeholder；生成资料清单并推送；访谈日历 |
| **门禁（内部）** | 资料清单已发出且客户确认收到；访谈已排期 ≥ 5 人 |

**项目章程必含 4 项：**
1. 诊断要回答的 3 个问题（由客户提出，顾问收敛）
2. 明确不做什么（防止范围蔓延）
3. 时间与双方投入
4. 交付物清单与验收方式

> 第 1 项是全阶段最重要的锚。如果客户说"我们想全面 AI 化"，就把它翻译成"我们想搞清楚哪三个环节最值得先做"。

---

### S1.2 现状诊断（5–8 天）

四维并行盘点：**业务、数据、系统、组织**。

#### ① 业务维度

| 活动 | 产出 |
|---|---|
| 访谈业务负责人与一线 | 业务流程图（现状，不是理想态） |
| 现场观察半天 | 实际操作的"隐性步骤"（Excel、微信群、纸质单） |
| 取数：单量、耗时、异常率 | 基线数据 |

**业务流程图必须让业务负责人逐条确认并签字（或系统内点击确认）。** 这是后续所有推行的基础。

#### ② 数据维度

| 盘点对象 | 必填字段 |
|---|---|
| 数据对象（订单/车辆/轨迹/单证/财务） | 名称、来源系统、格式、日增量、历史跨度 |
| 质量 | 完整率、准确率（抽样）、是否有唯一 ID |
| 可得性 | 能直接取 / 需开发 / 需申请 / 拿不到 |
| 责任方 | 谁维护、谁能批 |

> **必须做抽样验证。** "我们数据都有" 和 "我们数据能用来训练" 是两件事。抽 100 条看字段缺失率，10 分钟就能戳破幻觉。

#### ③ 系统维度

| 系统 | 厂商 | 版本 | 有无 API | 能否导出 | 谁维护 | 年费 |
|---|---|---|---|---|---|---|
| TMS | | | | | | |
| 财务 | | | | | | |
| GPS/北斗 | | | | | | |
| 报关/单一窗口 | | | | | | |

#### ④ 组织维度

| 部门 | 人数 | 数字化能力 | 变革意愿 | 决策链 |
|---|---|---|---|---|
| | | 高/中/低 | 支持/中立/抵触 | 谁说了算 |

**组织维度最容易被跳过，但它是项目失败的第一原因。** 一个技术上完美的方案，如果调度主管抵触，上线即失败。

#### 输出

| 交付物 | 说明 |
|---|---|
| 访谈纪要 ×N | 录音转写 + 摘要 + 原话摘录，客户可确认 |
| 现状业务流程图 | 经业务负责人确认 |
| 四维盘点表 | 完成度 ≥ 80% |
| 痛点清单 | ≥ 10 条，**每条必须有来源**（哪次访谈第几分钟 / 哪份数据） |

**痛点清单的字段：**

```
痛点ID | 描述（用客户原话） | 影响环节 | 量化影响 | 频率 | 严重度 | 现有应对方式 | 来源
```

> "量化影响"允许写"待确认"，但不允许写"很大"。

### S1.3 机会识别与价值评估（3–5 天）

#### 从痛点到机会点：不是一对一

多个痛点可能对应一个机会点，一个痛点也可能拆成多个机会点。

```
痛点：单证每天手工录 200 单，加班到 8 点
  ↓ 归并
机会点：订单/托书自动结构化录入
  ↓ 展开
假设：解析准确率 ≥ 95%
假设：单证岗工作量可释放 60%
假设：微信渠道可转为转发入口
```

> **一个机会点 = 一组可被验证的假设 + 一个可量化的价值。**

#### 评分模型

| 维度 | 符号 | 取值 | 评分依据 |
|---|---|---|---|
| 价值 | V | 1–5 | 年化财务影响 |
| 可行性 | F | 1–5 | 数据 40% + 技术 30% + 组织 30% |
| 数据就绪度 | D | 1–5 | 单独展示，不进公式（用于提示风险） |
| 紧迫性 | U | 0.8 / 1.0 / 1.2 | 有硬性时间要求（如政策、客户要求）则 1.2 |

**优先级分：`P = V × F × U`**（满分 30）

| 分值 | 建议 |
|---|---|
| ≥ 20 | 优先做，进入路线图第一期 |
| 12–19 | 候选，视资源安排 |
| < 12 | 搁置（Parked），记录原因 |

**V 的评分锚点（以年化收益计）：**

| 分 | 年化收益 | 或 |
|---|---|---|
| 5 | > 500 万 | 战略必须（合规/客户强制） |
| 4 | 100–500 万 | 明显竞争优势 |
| 3 | 30–100 万 | 效率改善 |
| 2 | 10–30 万 | 局部优化 |
| 1 | < 10 万 | 难以量化 |

**F 的评分锚点：**

| 分 | 数据 | 技术 | 组织 |
|---|---|---|---|
| 5 | 已有、干净、可直接取 | 成熟方案、无集成 | 业务方主动要 |
| 3 | 有但需清洗/申请 | 需定制开发 | 中立 |
| 1 | 拿不到 / 质量极差 | 需自研 | 明确抵触 |

#### ROI 模型

每个机会点一张卡，字段固定：

```
机会点名称
├─ 收益类型：降本 / 提效 / 增收 / 风险规避
├─ 基线：指标名 + 当前值 + 数据来源 + 采集日期 + 采集人
├─ 目标：指标名 + 目标值
├─ 计算逻辑：（公式，可被复核）
├─ 年化收益：保守 / 中性 / 乐观
├─ 投入：一次性 + 年运维
├─ 回本周期
├─ 置信度：高 / 中 / 低（取决于基线是否真实、假设是否已验证）
└─ 假设清单：每条带验证状态（未验证 / 已验证 / 已推翻）
```

**示例（集卡订单解析）：**

| 项 | 值 |
|---|---|
| 基线 | 单证岗 5 人，日均 200 单，单均 10 分钟，来源：2026-09 现场计时 + 排班表 |
| 目标 | 单均 3 分钟 |
| 计算 | (10−3) min × 200 单 ÷ 60 ÷ 8h ≈ 2.9 FTE → 按 10 万/人 ≈ 29 万/年 |
| 投入 | 首年 40 万（SaaS + 实施 + API） |
| 回本 | ≈ 16 个月 |
| 置信度 | 中（基线真实，但"释放人力"未必兑现） |
| 假设 | ① 准确率 ≥95%（未验证）② 微信可转入口（未验证）③ 释放人力可转岗（未验证） |

> **置信度"低"的机会点不是不能做，而是必须先进 POC。** 系统要把这个逻辑写死。

#### 输出

| 交付物 | 说明 |
|---|---|
| **机会地图** | 二维矩阵图（V × F），气泡大小 = ROI |
| 机会点卡片 ×3–5 | 每个含评分、ROI、假设清单、证据链接 |
| 数据可得性报告 | 按机会点标注数据状态 |
| 技术阻断项清单 | 若有，明确"这个不能做"及原因 |

### S1.4 路线图与决策简报（2–3 天）

| 活动 | 产出 |
|---|---|
| 机会点排序与分期 | 路线图（第一期/第二期/观望） |
| 第一期选型 | 建议 1–2 个机会点做 POC |
| 写一页纸简报 | 给决策人 |
| 拼装完整诊断报告 | 给项目负责人 |
| G1 内部评审 | 通过/打回 |

**分期原则：**
- 第一期：低成本 + 高确定性 + 能快速出证据（建立信任）
- 第二期：高价值 + 中等难度（扩大战果）
- 观望：价值高但数据不具备（等条件成熟）

> **不要第一期就上最难的。** 客户需要先看到一次成功，才愿意投第二次。

## 4. 诊断工具体系（系统内置 5 张表）

| # | 工具 | 用途 | 字段数 | 谁填 |
|---|---|---|---|---|
| 1 | 干系人图谱 | 谁影响决策、谁抵触 | 8 | 顾问 |
| 2 | 四维盘点表 | 业务/数据/系统/组织 | 32 | 顾问 + 客户 IT |
| 3 | 痛点清单 | 问题归集 | 8 | 顾问 |
| 4 | 机会点卡 | 评估与追踪 | 15 | 顾问 + 技术 |
| 5 | ROI 模型表 | 算账 | 12 | 顾问 + 客户财务 |

**模板的价值在于：** 新人拿着 5 张表就能跑完一次诊断。这是"方法论沉淀"的具体形态。

## 5. G1 诊断门禁清单

> 8 项全过才能进入 S2。缺项打回，不允许"先往下走回头补"。

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 业务流程图 | 经业务负责人确认（有确认记录） |
| 2 | 访谈完成度 | ≥ 5 人，纪要归档且可检索 |
| 3 | 四维盘点 | 完成度 ≥ 80%，数据维度必须有抽样结果 |
| 4 | 痛点清单 | ≥ 10 条，100% 有来源 |
| 5 | 机会点 | ≥ 3 个，每个有 V/F/U 评分及理由 |
| 6 | 基线数据 | 至少 1 个机会点有真实基线（非行业均值） |
| 7 | 技术阻断项 | 已识别并记录（或明确标注"无"） |
| 8 | 一页纸简报 | 已生成，且 PM 审核通过 |

**第 6 项是硬门槛。** 没有真实基线的 ROI 一律标记置信度"低"，且不能作为第一期推荐。

## 6. 系统功能映射（MVP 必须做的页面）

| 页面 | 核心能力 |
|---|---|
| 项目详情 | 阶段时间轴、当前门禁状态、待办、参与人 |
| 干系人管理 | 录入、影响力/态度矩阵、关注点标签 |
| 访谈工作台 | 上传录音 → 转写 → AI 摘要 → 一键抽取痛点 → 人工确认 |
| 四维盘点 | 四个 Tab 的表单，支持批量导入 Excel |
| 痛点库 | 列表 + 来源追溯 + 归并到机会点 |
| **机会地图** | 矩阵图 + 列表切换，点击进卡片 |
| 机会点卡片 | 评分、假设清单、ROI、证据、技术阻断项 |
| ROI 计算器 | 输入基线/目标/投入，实时出回本周期与敏感性 |
| 交付物中心 | 模板选择 → 变量填充 → 生成 Word/PPT/PDF → 版本管理 |
| 客户门户 | 只读进度、待办、待批、下载交付物 |
| 决策记录 | 谁、何时、基于什么、做了什么决定 |

**MVP 可以砍掉的：** 甘特图、工时统计、计费、多语言、移动端 App。

## 7. 客户侧一页纸简报（样例）

> 这份东西是 S1 的最终产品。系统应能从这个阶段的所有结构化数据自动生成它。

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
XX 物流 · AI 化诊断简报
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

【结论】
建议先做"订单自动录入"，16 个月回本；
暂不建议做"智能调度"，数据条件还不具备。

【现状三个数字】
· 100 台集卡，年营收约 4,800 万，净利率 3%–6%
· 单证岗 5 人，日均 200 单，单均 10 分钟
· 空驶率约 35%，高于行业良好水平（25%）

【机会地图】
  高价值 │  ②异常费用追收    ①订单自动录入
        │
  低价值 │  ③客户自助查询    ④智能调度(暂缓)
        └──────────────────────────────
          低可行性              高可行性

【推荐第一步】
① 订单/托书自动结构化录入
   投入：40 万（首年）  年化收益：约 29 万  回本：16 个月
   第一步只做微信渠道，2 个月出结果

【需要您拍板】
1. 是否同意先做 8 周 POC（预算 15 万）
2. 指定一位业务负责人参与验收
3. 同意开放订单历史数据（只读）

【主要风险】
· 数据需客户 IT 配合开放接口
· 一线需要改变"微信发单"习惯
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 8. 常见失败模式

| # | 失败模式 | 后果 | 系统如何防 |
|---|---|---|---|
| 1 | 访谈变成"需求收集会" | 拿到一堆"我想要"，拿不到"现在是什么样" | 访谈模板强制区分"现状"与"期望" |
| 2 | 只访谈老板，不见一线 | 方案脱离实际，上线失败 | 干系人图谱强制包含 ≥2 名一线 |
| 3 | 跳过数据抽样 | 技术上不可行，后期返工 | 数据维度必填"抽样结果" |
| 4 | 机会点太多不排序 | 客户无法决策 | 强制 P 值排序，一期最多 2 个 |
| 5 | ROI 用行业均值 | 数字好看但不可信 | 无基线则置信度锁死为"低" |
| 6 | 报告写成技术方案 | 老板看不懂，不批预算 | 强制生成一页纸，且必须由 PM 审核 |
| 7 | 客户 owner 没参与 | 内部推不动 | 项目章程必须由 owner 签字确认 |
| 8 | 诊断一结束就报价 | 客户觉得你在卖东西 | S1 不产出报价，只产出"建议" |

## 9. 与 S2 的衔接

S1 的输出直接决定 S2 的输入：

| S1 产出 | S2 用途 |
|---|---|
| 机会点卡片 | → 方案设计对象 |
| 假设清单 | → POC 实验设计 |
| 基线指标 | → 验收标准 |
| 技术阻断项 | → 架构约束 |
| 干系人图谱 | → 沟通计划 |
| 路线图 | → 分期报价 |

**最关键的衔接：假设清单直接变成 S3 的 POC 验证清单。**
假设 → 实验 → 结论，这条链路一旦在系统里连通，整个交付就闭环了。
