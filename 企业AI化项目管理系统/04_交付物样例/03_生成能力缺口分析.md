# 生成能力缺口分析

> 用「宏远物流」真实数据跑一遍完整诊断报告后，发现的 12 个缺口，以及自动化率评估。

## 结论先行

| 判断 | 结论 |
|---|---|
| 能不能生成一份给客户看的报告 | **能**，v1 模板已可用 |
| 能不能生成一份让客户"信"的报告 | **还不能**，缺三样东西 |
| 自动化率 | **约 62%**（按章节加权） |
| 最大缺口 | ① 业务流程图无法图形化 ② 无行业对标基准 ③ ROI 无敏感度分析 |
| 结论 | **数据模型基本够用，缺的是 5 张表和 3 个计算规则** |

> 一句话：**能自动写"是什么"，还不能自动写"所以呢"。**

---

## 一、12 个具体缺口

### A 类：数据模型缺表（5 个，必须补）

#### A1 · 业务流程图无法生成 ★★★

| 项 | 内容 |
|---|---|
| 现象 | 报告第 2.1 节的流程链条是手写的。`inventory_items` 只有文字行，没有节点、连线、角色泳道 |
| 影响 | 流程图是诊断报告里客户最先看、也最认的东西。没有它，报告像"数据汇总"而不是"诊断" |
| 建议 | 新增 `process_nodes`（节点、角色泳道、耗时、异常率）和 `process_edges`（from/to、条件） |
| 成本 | 中（要配一个拖拽画布） |

#### A2 · 行业对标基准缺失 ★★★

| 项 | 内容 |
|---|---|
| 现象 | 报告里"空驶率 35%，行业良好水平约 25%"——**这个 25% 没有来源，是我凭经验写的** |
| 影响 | 没有对标，客户不知道 35% 是好是坏。这是诊断报告"专业感"的核心 |
| 建议 | 新增 `benchmarks(industry, sub_industry, metric, p25, p50, p75, source, year)`，做成可维护的行业库 |
| 成本 | 低（建表）+ 持续投入（数据采集） |

#### A3 · 客户财务数据未入库 ★★

| 项 | 内容 |
|---|---|
| 现象 | `clients.annual_revenue` 字段存在，但原型里没有值。报告只能标注"售前资料，未复核" |
| 影响 | 所有基于营收的 ROI（如 OP-02 的 36 万）误差可达 ±30% |
| 建议 | 新增 `client_financials(指标, 值, 期间, 来源, 是否审计)`，与 `baselines` 同构 |
| 成本 | 低 |

#### A4 · 机会点依赖关系没建模 ★★

| 项 | 内容 |
|---|---|
| 现象 | 报告写"OP-02 前置条件是先统一费用数据口径"——这个依赖关系只存在于文字里 |
| 影响 | 排期时会漏掉前置任务；一期做完了发现二期做不了 |
| 建议 | 新增 `opportunity_dependencies(from_id, to_id, type: blocks/requires/enables)` |
| 成本 | 低 |

#### A5 · 收益的"实现形态"没有字段 ★★

| 项 | 内容 |
|---|---|
| 现象 | ROI 只算金额（29 万/年），但没说这 29 万是**裁员、不增人、还是转岗** |
| 影响 | 这是 AI 项目 ROI 最大的争议点。报告里我只能手写一段解释 |
| 建议 | `roi_models` 增加 `realization_mode`（cut / no_headcount_growth / redeploy / revenue），不同模式给不同折算系数 |
| 成本 | 低（字段）+ 中（系数需要行业经验值） |

### B 类：有数据但缺计算规则（4 个）

#### B1 · ROI 没有敏感度分析 ★★★

| 项 | 内容 |
|---|---|
| 现象 | 只有保守/中性/乐观三档。客户一定会问"如果准确率只有 85% 呢？"——系统答不出来 |
| 影响 | 决策人最关心的不是最好情况，是**最坏情况能不能承受** |
| 建议 | 新增 `roi_sensitivity(opportunity_id, variable, from, to, impact)`，模板输出一张龙卷风图或小表 |
| 成本 | 中 |

#### B2 · 组织准备度只有标签，没有分数 ★★

| 项 | 内容 |
|---|---|
| 现象 | 组织维度有"支持/中立/抵触"，但无法算出一个总分 |
| 影响 | 无法在多项目间横向比较"哪家客户更容易推" |
| 建议 | 定义 `org_readiness = f(关键人态度, 支持者比例, 抵触者影响力)` |
| 成本 | 低 |

#### B3 · 隐性环节无处存放 ★★

| 项 | 内容 |
|---|---|
| 现象 | 本次最有价值的发现——"微信转单、口头催单、Excel 对账"——在盘点表里没有字段 |
| 影响 | 这些恰恰是 AI 机会的主要来源，却最容易在结构化过程中丢失 |
| 建议 | `inventory_items` 增加 `is_implicit` 布尔 + `discovered_by`（访谈/观察）；报告单列一节 |
| 成本 | 极低 |

#### B4 · "本次诊断的局限"无法自动生成 ★

| 项 | 内容 |
|---|---|
| 现象 | 这一段是我人工写的，但逻辑是规则的：把所有 `confidence=low` 的基线汇总 |
| 影响 | 每份报告都要人工想一遍，且容易漏 |
| 建议 | 增加 `confidence_summary` 视图，模板变量 `{{limitations}}` |
| 成本 | 极低 |

### C 类：流程与模板缺口（3 个）

#### C1 · 痛点饱和度没有检查 ★★

| 项 | 内容 |
|---|---|
| 现象 | G1 要求 ≥10 条，实际 8 条。系统只在门禁上显示"8/10"，但**不告诉顾问还缺哪一类** |
| 建议 | 按"角色 × 环节"做覆盖度矩阵，标出空白格（如"司机端 × 装柜"未覆盖） |
| 成本 | 低 |

#### C2 · 门禁清单与报告没有绑定 ★

| 项 | 内容 |
|---|---|
| 现象 | 附录 C 的 G1 状态是手工抄的。`gates.checklist` 已经存在，但模板没绑定 |
| 建议 | 模板变量 `{{gate_checklist}}`，直接渲染 |
| 成本 | 极低 |

#### C3 · 交付物没有模板版本与生成快照 ★

| 项 | 内容 |
|---|---|
| 现象 | 报告是 v1.0，但没记录用的是哪版模板、生成时数据是什么状态 |
| 影响 | 三个月后客户问"当时为什么是 29 万"，无法复现 |
| 建议 | `deliverables` 增加 `template_id` + `generated_snapshot`（jsonb 快照） |
| 成本 | 低 |

## 二、自动化率评估（按章节）

| 章节 | 内容 | 自动化率 | 说明 |
|---|---|---|---|
| 摘要 | 结论 + 三期表 | 70% | 表自动，结论句需人工 |
| 1 诊断范围 | 方法、边界 | 95% | 模板 |
| 2 业务现状 | 流程图 + 量化表 | 60% | **流程图需人工**，表自动 |
| 3 四维诊断 | 四张表 + 结论 | 55% | 表自动，结论需人工 |
| 4 痛点清单 | 8 条 | 100% | 全自动 |
| 5 机会地图 | 评分 + 矩阵 | 100% | 全自动 |
| 6 ROI 测算 | 4 张卡 | 95% | 全自动 |
| 7 推荐路线 | 分期 | 30% | **判断部分必须人工** |
| 8 风险 | 表 + 应对 | 70% | 风险自动，应对需人工 |
| 9 局限说明 | 3 条 | 80% | 可规则生成 |
| 附录 A/B/C | 清单 | 100% | 全自动 |

**加权平均：约 62%**

## 三、哪些必须人工（这很重要）

有三处，我明确建议**永远不要让 AI 自动生成**：

| # | 内容 | 为什么 |
|---|---|---|
| 1 | **推荐路线里的"为什么不是它"** | 报告里写"第一期选 OP-01 而不是 ROI 最高的 OP-02，因为基线真实性不同"——这是判断，不是数据。AI 生成会变成正确的废话 |
| 2 | **业务流程图的节点划分** | 颗粒度怎么切，取决于顾问的经验。切太细看不懂，切太粗没价值 |
| 3 | **风险应对措施** | "安排一次单独沟通"这种话，需要知道客户内部的人际关系 |

> **原则：数据归系统，判断归人。** 系统可以把判断的**依据**准备好，但不能替人下判断。

## 四、v2 需要补的 5 张表

```sql
-- 1. 行业对标基准
benchmarks(industry, sub_industry, metric, p25, p50, p75, source, year)

-- 2. 客户财务快照
client_financials(client_id, metric, value, period, source, audited, confidence)

-- 3. 机会点依赖
opportunity_dependencies(from_id, to_id, type)

-- 4. ROI 敏感度
roi_sensitivity(opportunity_id, variable, from_value, to_value, impact_value)

-- 5. 业务流程节点
process_nodes(engagement_id, lane, name, owner, duration, abnormal_rate, is_implicit)
process_edges(from_id, to_id, condition)
```

**外加 3 个字段改动：**

| 表 | 字段 | 说明 |
|---|---|---|
| `roi_models` | `realization_mode` | cut / no_headcount_growth / redeploy / revenue |
| `inventory_items` | `is_implicit` | 隐性环节标记 |
| `deliverables` | `template_id`, `generated_snapshot` | 可复现 |

## 五、对下一步的影响

| 建议 | 理由 |
|---|---|
| **MVP 仍然只做 S1，但把 A1/A2/B1 纳入** | 这三项直接决定报告能不能用。其余可延后 |
| **行业对标库先手工维护 20 个指标** | 不需要一开始就建大库，物流行业 20 个核心指标足够 |
| **敏感度分析先做单变量** | 客户最常问的就是"准确率只有 85% 怎么办"，回答这一个就够 |
| **不要做业务流程图的自动生成** | 做画布让人画，不要做算法 |

## 六、这次实测验证了什么

| 设计假设 | 验证结果 |
|---|---|
| "数字全部来自数据库，AI 只负责措辞" | ✅ 成立。报告中所有数字都能追到来源 |
| "四条硬规则" | ✅ 成立。OP-05 的技术阻断、OP-02 的低置信度，都在报告里自然体现 |
| "假设清单 → POC 验证清单" | ✅ 成立。OP-01 的 4 条假设直接变成了 POC 的验证项 |
| "交付物自动生成" | ⚠️ 部分成立。62% 可自动，判断部分仍需人 |
| "客户侧不用登录" | ✅ 成立。报告本身就是交付物，不需要门户 |

**总体判断：这套系统的核心机制是对的，缺的是行业数据的厚度，不是架构。**
