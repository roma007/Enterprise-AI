## 1. `benchmarks` · 行业对标基准

### 1.1 解决什么问题

v1 的报告里写"空驶率 35%，行业良好水平约 25%"——**这个 25% 没有来源**。没有对标的诊断报告，客户无法判断好坏，专业感直接归零。

### 1.2 DDL

```sql
CREATE TABLE benchmarks (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  industry      text NOT NULL,              -- 'logistics'
  sub_industry  text NOT NULL DEFAULT '',   -- 'port_container_trucking'
  metric_key    text NOT NULL,              -- 'empty_run_rate'
  metric_name   text NOT NULL,              -- '空驶率'
  unit          text NOT NULL,              -- '%'
  direction     text NOT NULL CHECK (direction IN ('higher_better','lower_better')),
  p25           numeric,                    -- 优秀（25 分位）
  p50           numeric,                    -- 中位
  p75           numeric,                    -- 落后（75 分位）
  source        text NOT NULL,              -- '行业经验值 · 待校准'
  source_url    text,
  sample_size   int,
  year          int  NOT NULL,
  region        text NOT NULL DEFAULT 'CN',
  calibrated    boolean NOT NULL DEFAULT false,  -- 是否经过实测校准
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (industry, sub_industry, metric_key, year, region)
);

CREATE INDEX ON benchmarks (industry, metric_key);
```

> `sub_industry` 必须有默认值 `''` 而不是 NULL —— 否则 PostgreSQL 的唯一约束对 NULL 失效。

### 1.3 新增计算：客户分位定位

报告里需要的不只是基准值，而是**"你在行业里处于什么位置"**。

**边界规则（已定，v2.1）：触发「落后」的那条边界归入落后一档，其余边界归入较好一档。**

理由：`p75`（低优指标）或 `p25`（高优指标）是**唯一会触发行动的阈值**——客户被判"落后"才会分配资源。这条线宁可误报，不可漏报；而 `p25`/`p50` 处的分档只影响措辞，归优可以减少无谓的紧张。

```sql
-- 输入：客户指标值 v（如空驶率 35）
-- 输出：分位区间（excellent / good / median / lagging / unknown）
-- 边界规则：落后那条边界归落后，其余边界归优。
--   lower_better：<= p25 优秀 | < p50 良好 | < p75 中位 | >= p75 落后
--   higher_better：>= p75 优秀 | > p50 良好 | > p25 中位 | <= p25 落后
CREATE OR REPLACE FUNCTION benchmark_position(
  p_industry text, p_metric_key text, p_value numeric
) RETURNS text AS $$
DECLARE b benchmarks;
BEGIN
  SELECT * INTO b FROM benchmarks
   WHERE industry = p_industry AND metric_key = p_metric_key
     AND year = EXTRACT(YEAR FROM now())::int
   LIMIT 1;
  IF NOT FOUND THEN RETURN 'unknown'; END IF;

  IF b.direction = 'lower_better' THEN
    RETURN CASE
      WHEN p_value <= b.p25 THEN 'excellent'
      WHEN p_value <  b.p50 THEN 'good'
      WHEN p_value <  b.p75 THEN 'median'
      ELSE 'lagging' END;          -- 含 p_value = p75
  ELSE
    RETURN CASE
      WHEN p_value >= b.p75 THEN 'excellent'
      WHEN p_value >  b.p50 THEN 'good'
      WHEN p_value >  b.p25 THEN 'median'
      ELSE 'lagging' END;          -- 含 p_value = p25
  END IF;
END $$ LANGUAGE plpgsql;
```

**边界命中时的报告措辞（必须照此写，不要四舍五入掉）：**

> 单均录入耗时 10 分钟，行业 p75 = 10 分钟，**恰在边界上，按规则判定为「落后」**。

不要写成"约等于行业中位"。边界值必须原样呈现并说明判定，否则客户拿自己的数据一算，会觉得报告在含糊其辞。

**报告输出效果：**

> 空驶率 35%，行业 p50 = 30%，p75 = 38%，**处于"中位"区间，落后于良好水平**。

比"行业良好水平约 25%"可信得多，因为 25/30/38 都能查到来源。

### 1.4 数据维护策略

| 阶段 | 做法 |
|---|---|
| MVP | 手工维护 20 个物流核心指标（见附录 A），标注 `calibrated=false` |
| 6 个月后 | 用自有项目的真实基线反哺，`calibrated=true` |
| 1 年后 | 形成"行业基准库"，成为产品护城河 |

> **这是少数几个越用越值钱的模块。** 每做完一个项目，基准库就厚一点。

## 2. `client_financials` · 企业财务快照

### 2.1 解决什么问题

`clients.annual_revenue` 是个单值字段，没有期间、没有来源、没有置信度。报告只能标"售前资料，未复核"，所有基于营收的 ROI 误差可达 ±30%。

### 2.2 DDL

```sql
CREATE TABLE client_financials (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  client_id    uuid NOT NULL REFERENCES clients(id) ON DELETE CASCADE,
  metric_key   text NOT NULL,          -- 'annual_revenue' / 'net_margin' / 'gross_margin'
  value        numeric NOT NULL,
  unit         text NOT NULL,          -- '万元' / '%'
  period_start date NOT NULL,
  period_end   date NOT NULL,
  source_type  text NOT NULL CHECK (source_type IN ('audited','management','estimate','public')),
  source_note  text,                   -- '2025 年审计报告' / '张总口述'
  confidence   text NOT NULL CHECK (confidence IN ('high','medium','low')),
  verified_by  uuid REFERENCES stakeholders(id),
  created_at   timestamptz NOT NULL DEFAULT now(),
  UNIQUE (client_id, metric_key, period_start)
);
```

### 2.3 与 `baselines` 的区别（重要）

| 表 | 层级 | 用途 |
|---|---|---|
| `client_financials` | **企业级** | 年营收、净利率、毛利率。一个客户一份 |
| `baselines` | **场景级** | 单均耗时、错单次数、空驶率。一个机会点一份 |

**为什么必须分开：** 企业财务数据是"背景"，场景基线是"证据"。混在一张表里，会导致"营收数据"被当成某个机会点的基线，从而错误地提升置信度。

### 2.4 规则联动

> **R2 的扩展：** 当 ROI 计算引用了 `client_financials` 且其 `confidence='low'` 时，该 ROI 的置信度**不得高于 low**。
> 这条规则直接作用于 OP-02（36 万收益基于未复核的 4,800 万营收）。

## 3. `opportunity_dependencies` · 机会点依赖

### 3.1 解决什么问题

v1 报告里写"OP-02 的前置条件是先统一费用数据口径"——这个依赖只存在于文字里，排期时会漏掉。

### 3.2 DDL

```sql
CREATE TABLE opportunity_dependencies (
  id       uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  from_id  uuid NOT NULL REFERENCES opportunities(id) ON DELETE CASCADE,
  to_id    uuid NOT NULL REFERENCES opportunities(id) ON DELETE CASCADE,
  type     text NOT NULL CHECK (type IN ('requires','blocks','enables')),
  note     text,
  created_at timestamptz NOT NULL DEFAULT now(),
  CHECK (from_id <> to_id)
);

CREATE UNIQUE INDEX ON opportunity_dependencies (from_id, to_id, type);
CREATE INDEX ON opportunity_dependencies (to_id);
```

### 3.3 语义

| type | 含义 | 示例 |
|---|---|---|
| `requires` | from 依赖 to 先完成 | OP-02 requires OP-03（费用核对要先有单证核对） |
| `blocks` | from 阻塞 to | OP-05 blocks OP-06（调度没解决，回程匹配无意义） |
| `enables` | from 为 to 创造条件 | OP-01 enables OP-04（订单结构化后，查询才有数据） |

### 3.4 无环校验

```sql
-- 检测环：返回构成环的节点
WITH RECURSIVE walk(start_id, cur_id, path, depth) AS (
  SELECT from_id, to_id, ARRAY[from_id, to_id], 1
    FROM opportunity_dependencies WHERE type = 'requires'
  UNION ALL
  SELECT w.start_id, d.to_id, w.path || d.to_id, w.depth + 1
    FROM walk w
    JOIN opportunity_dependencies d ON d.from_id = w.cur_id AND d.type = 'requires'
   WHERE NOT (d.to_id = ANY(w.path)) AND w.depth < 20
)
SELECT DISTINCT start_id FROM walk WHERE cur_id = start_id;
```

**规则：`requires` 关系必须无环。** `blocks` 和 `enables` 允许成环（它们不是排期约束）。

## 4. `roi_sensitivity` · ROI 敏感度

### 4.1 解决什么问题

客户一定会问："如果准确率只有 85% 呢？"——v1 只有保守/中性/乐观三档，答不出来。
**决策人关心的不是最好情况，是最坏情况能不能扛。**

### 4.2 DDL

**v2.1 改动：从"平铺的变量列表"改为"有顺序的传导链"。**

```sql
CREATE TABLE roi_sensitivity (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  opportunity_id uuid NOT NULL REFERENCES roi_models(opportunity_id) ON DELETE CASCADE,

  stage          int  NOT NULL CHECK (stage >= 1),  -- 传导链位置，必须从 1 连续
  variable_key   text NOT NULL,        -- 'channel_coverage' / 'accuracy' / 'adoption'
  variable_label text NOT NULL,        -- '微信渠道覆盖'
  unit           text,                 -- '%' / '单/日'

  base_value     numeric,              -- 基准取值（给人看）
  low_value      numeric,              -- 悲观取值
  high_value     numeric,              -- 乐观取值

  -- 折算系数：这一段把上游金额乘掉多少（0–1）
  mult_base      numeric NOT NULL CHECK (mult_base  BETWEEN 0 AND 1),
  mult_low       numeric          CHECK (mult_low   BETWEEN 0 AND 1),
  mult_high      numeric          CHECK (mult_high  BETWEEN 0 AND 1),

  shape          text NOT NULL DEFAULT 'linear'
                 CHECK (shape IN ('linear','threshold')),  -- 见 4.5
  controllable   boolean NOT NULL DEFAULT true,  -- 顾问/客户能否主动影响
  owner_role     text,                            -- 谁负责守住这一段
  is_derived     boolean NOT NULL DEFAULT false,  -- 仅展示用，不参与计算
  depends_on     text[]  NOT NULL DEFAULT '{}',   -- 派生变量的上游 variable_key

  note           text,
  created_at     timestamptz NOT NULL DEFAULT now(),
  UNIQUE (opportunity_id, variable_key),
  UNIQUE (opportunity_id, stage)
);
```

**两个关键约束：**

| 约束 | 为什么 |
|---|---|
| `UNIQUE (opportunity_id, stage)` | 传导链必须是**有序**的。没有序号，乘法的先后就没了，等于退回平铺列表 |
| `stage` 必须从 1 开始连续 | 中间断号意味着漏了一段，链条算不通。用应用层校验（PostgreSQL 不好写跨行 CHECK） |

### 4.3 计算规则与一致性校验

```
realized_value = neutral_value × mult_base(stage 1) × mult_base(stage 2) × … × mult_base(stage n)
```

即：**`realization_factor` 不是拍出来的一个数，而是这条链上各段系数的乘积。**

这带来一条新的硬校验：

> **R5-C12：`|∏ mult_base − realization_factor| ≤ 0.005`，否则 block。**
>
> 防止两件事同时发生：① 顾问改了某一段的系数，忘了改总系数；② 总系数是拍出来的，链条是事后编的。这两件事只要有一件，报告里的"因果"就是假的。

### 4.4 示例（OP-01）

**传导链（基准情形）：**

| 段 | 变量 | 取值 | 系数 | 可干预 | 责任方 |
|---|---|---|---|---|---|
| 起点 | 理论年化收益 | — | 29.0 万 | — | — |
| 1 | 微信渠道覆盖（一线愿不愿意发到统一入口） | 100% | ×1.00 | ✅ | 客户运营 |
| 2 | 托书字段准确率（≥90% 才有意义） | 95% | ×0.95 | ✅ | 供应商 |
| 3 | 单证员实际采用率（拿到结果后用不用） | 100% | ×0.70 | ✅ | 客户单证组 |
| 4 | 释放的时间转为财务价值 | — | ×0.90 | ❌ | 管理层 |
| 终点 | **可实现年化收益** | — | **17.4 万** | — | — |

`1.00 × 0.95 × 0.70 × 0.90 = 0.5985` → `29 × 0.5985 = 17.36 ≈ 17.4 万`

> **顺带解释了那个"0.6"是怎么来的。** 之前说"按 0.6 折算"，客户会问"凭什么 0.6"。
> 现在能答：**0.6 = 0.95（准确率）× 0.70（采用率）× 0.90（价值转化）**。三段各有依据，可以逐段质疑、逐段验。

**单段恶化（其余各段保持基准）：**

| 恶化的段 | 悲观取值 | 系数变化 | 可实现收益 | 损失 |
|---|---|---|---|---|
| 微信渠道覆盖 | 100% → 60% | 1.00 → 0.60 | 10.4 万 | **−7.0 万** |
| 单证员实际采用率 | 100% → 60% | 0.70 → 0.42 | 10.4 万 | **−7.0 万** |
| 托书字段准确率 | 95% → 85% | 0.95 → 0.85 | 15.5 万 | −1.9 万 |
| 价值转化（管理层口径） | 0.90 → 0.60 | 0.90 → 0.60 | 11.6 万 | −5.8 万 |

**结论没变，但现在能证明：**

> **准确率只损 1.9 万，不是因为模型不重要，而是因为它的可恶化空间只有 10 个百分点；渠道覆盖和采用率的可恶化空间是 40 个百分点。**
> **敏感度 = 恶化幅度 × 对收益的弹性，两者都要看。**

### 4.5 为什么放弃龙卷风图（P4 决策）

两个原因，第二个更要紧。

**原因一：派生变量会造成假旋钮。**

原来的表里有一行"单证岗实际释放比例 30%–80%"，摆动 14.5 万，看着最致命。但它其实是第 1、3 段的**结果**，不是可以单独拧的旋钮。客户会问"那我们把释放比例拉到 80% 行不行"——这个问句没有对应的操作。

> 处理方式：派生变量不再作为独立输入。链条上只放**可操作的段**（渠道、准确率、采用率、口径），"释放比例"作为中间结果在图上标出来，用虚线连接，不参与乘法和排序。

**原因二：龙卷风图默认变量是线性的，但准确率是阈值型的。**

准确率 95% → 85%，线性模型算出"损失 1.9 万"，看起来无关痛痒。真实情况是：

```
准确率 ≥ 95%  → 免复核，采用率可达 100%
准确率 90–95% → 抽检 30%，采用率掉到约 70%
准确率 < 90%  → 全量复核，收益接近 0
```

**所以准确率是断崖型变量：在 90% 以上几乎不影响收益，跌破 90% 直接清零。**

一张线性龙卷风图会同时犯两个错：**高估** 93% 时的损失，**严重低估** 88% 时的损失。

> 处理方式：`shape = 'threshold'` 的变量在图上不画成条形，画成**带断崖标记的分段线**，并标注"低于 X% 收益归零"。
> 这也是 POC 必须先验证准确率的原因——不是因为它最敏感，而是因为**它有一个不可回退的悬崖**。

**新的图形（文字示意）：**

```
理论 29.0 万
   │
   ├─ ×1.00  渠道覆盖 100%          ────────────► 29.0
   │
   ├─ ×0.95  准确率 95%（断崖在 90%） ──────────► 27.6
   │
   ├─ ×0.70  采用率 100%            ────────────► 19.3
   │
   └─ ×0.90  价值转化               ────────────► 17.4  ← 可实现

   灰线（派生，不参与乘法）：实际释放比例 ≈ 66.5%
```

### 4.6 生成方式

| 方式 | 适用 | 说明 |
|---|---|---|
| `manual` | MVP 默认 | 顾问填各段取值与系数，系统只负责连乘和校验 |
| `formula` | 后续 | 段间函数关系自动推导，需要表达式引擎 |

**MVP 只做 `manual`。** 连乘和"乘积等于总系数"的校验已经能防住绝大多数错误，且实现成本极低。

## 5. `process_models` / `process_nodes` / `process_edges` · 业务流程图

### 5.1 解决什么问题

v1 的盘点表只有文字行，报告里的流程链是手打的。而流程图是客户最先看、也最认的东西。

### 5.2 DDL

```sql
-- 一个项目可以有多个版本的流程图
CREATE TABLE process_models (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  engagement_id uuid NOT NULL REFERENCES engagements(id) ON DELETE CASCADE,
  version       int NOT NULL DEFAULT 1,
  status        text NOT NULL DEFAULT 'draft'
                CHECK (status IN ('draft','confirmed','archived')),
  confirmed_by  uuid REFERENCES stakeholders(id),
  confirmed_at  timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (engagement_id, version)
);

CREATE TABLE process_nodes (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  model_id      uuid NOT NULL REFERENCES process_models(id) ON DELETE CASCADE,
  lane          text NOT NULL,            -- 泳道：单证组 / 调度组 / 司机 / 客户
  name          text NOT NULL,
  node_type     text NOT NULL CHECK (node_type IN
                ('start','end','action','decision','wait','system','manual')),
  owner_role    text,
  duration_min  numeric,                  -- 单次耗时（分钟）
  abnormal_rate numeric,                  -- 异常率 %
  is_implicit   boolean NOT NULL DEFAULT false,   -- 隐性环节
  discovered_by text CHECK (discovered_by IN ('interview','observation','data')),
  pos_x         numeric,
  pos_y         numeric,
  sort_order    int
);

CREATE TABLE process_edges (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  model_id     uuid NOT NULL REFERENCES process_models(id) ON DELETE CASCADE,
  from_node_id uuid NOT NULL REFERENCES process_nodes(id) ON DELETE CASCADE,
  to_node_id   uuid NOT NULL REFERENCES process_nodes(id) ON DELETE CASCADE,
  label        text,
  condition    text,                      -- 决策分支条件
  CHECK (from_node_id <> to_node_id)
);
```

### 5.3 关键设计：`is_implicit`

这是 v1 最大的漏洞。本次诊断最有价值的发现——**微信转单、口头催单、Excel 对账**——在 v1 的表结构里无处存放。

```sql
-- 隐性环节是 AI 机会的主要来源，报告必须单列
SELECT lane, name, discovered_by
  FROM process_nodes
 WHERE model_id = $1 AND is_implicit = true
 ORDER BY abnormal_rate DESC NULLS LAST;
```

**报告输出：**

> **三个"隐性环节"（不在任何流程文件里，但每天真实发生）：**
> 1. 微信转单（单证组）— 现场观察发现
> 2. 口头催单（调度组）— 访谈发现
> 3. Excel 对账（财务）— 现场观察发现
> **判断：这三个隐性环节，是本次 AI 机会的主要来源。**

### 5.4 为什么不做"自动生成流程图"

明确建议：**只做画布，不做算法。**

流程图的节点颗粒度取决于顾问经验——切太细看不懂，切太粗没价值。让 AI 生成节点划分，产出的永远是"看起来很专业但没法用"的东西。

**系统只负责：**
- 提供一个泳道画布（拖拽）
- 节点自动关联到痛点（`pain_points.process_node_id`）
- 版本管理与客户确认留痕

## 6. 字段变更

### 6.1 `roi_models` · 收益实现形态（最重要的一处）

**已定决策（v2.1）：系统不做判定，由顾问逐项选择；但必须留下判断痕迹。**

即：枚举只负责**记录**，不负责**裁决**。系统唯一强制的，是"不许含糊"——没有默认值、必须写理由、必须署名确认。

```sql
ALTER TABLE roi_models
  -- 注意：全部不给 DEFAULT。不给默认值就是约束：
  -- 顾问必须显式选择，否则写不进去（默认值会让所有人悄悄停在 revenue）
  ADD COLUMN realization_mode text
    CHECK (realization_mode IN
      ('cut','no_headcount_growth','redeploy','revenue','cost_avoidance')),
  ADD COLUMN realization_factor numeric
    CHECK (realization_factor >= 0 AND realization_factor <= 1),
  ADD COLUMN realization_note text,             -- 必填：为什么这么判（≥10 字）
  ADD COLUMN realization_confirmed_by uuid REFERENCES users(id),
  ADD COLUMN realization_confirmed_at timestamptz,
  ADD COLUMN realized_value numeric
    GENERATED ALWAYS AS (neutral_value * realization_factor) STORED,
  ADD CONSTRAINT realization_all_or_nothing CHECK (
    (realization_mode IS NULL AND realization_factor IS NULL
       AND realization_confirmed_at IS NULL)
    OR
    (realization_mode IS NOT NULL AND realization_factor IS NOT NULL
       AND realization_confirmed_at IS NOT NULL
       AND realization_note IS NOT NULL
       AND length(btrim(realization_note)) >= 10)
  );
```

**为什么要"全有或全无"而不只是 NOT NULL：**

ROI 卡在诊断早期是允许空着的（还没谈到收益形态）。真正危险的状态是**"填了一半"**——选了 `revenue` 却没人签名，三个月后没人承认这个判断是自己下的。约束强制三件事同时发生：选形态、定系数、署名。

**同时补一个 v1 遗漏的约束**（`roi_sensitivity` 的外键依赖它）：

```sql
ALTER TABLE roi_models
  ADD CONSTRAINT roi_models_opportunity_unique UNIQUE (opportunity_id);
```

> v1 假设一个机会点对应一张 ROI 卡（1:1），但没有加唯一约束。v2 的 `roi_sensitivity` 通过 `opportunity_id` 外键引用它，没有这个约束建表会失败。

**为什么这是 v2 最重要的一处改动：**

v1 的 ROI 只算"理论上能省多少钱"。但"省 2.9 个单证岗"在绝大多数公司**不会真的裁员**，实际收益形态是"业务量涨 30% 但人不增"。这两者的财务价值差很远。

| mode | 含义 | 建议区间（非强制） | 适用场景 |
|---|---|---|---|
| `cut` | 真裁员 | 1.0 | 极少见，且政治风险高 |
| `no_headcount_growth` | 不增人 | **0.6–0.8** | 最常见 |
| `redeploy` | 转岗到更高价值岗位 | 0.9 | 需要新岗位确实存在 |
| `revenue` | 直接增收 | 1.0 | 能开出新增发票、或本该收到未收到的钱 |
| `cost_avoidance` | 风险规避（罚款、事故） | 0.3–0.5 | 难量化，打折严重 |

> 「建议区间」列只是**填表时的默认提示**，不是校验规则。系统不因为顾问填了 0.75 而报错——但要他把理由写下来。

**顾问选择带来的副作用，以及怎么兜（重要）：**

同一个机会点，不同顾问可能判出不同结果。以 OP-02 为例：

| 判法 | 系数 | 可实现收益 | 一期回本 |
|---|---|---|---|
| `revenue`（费用追收 = 原本就该收到的钱） | 1.0 | 36 万 | 14.8 个月 |
| `cost_avoidance`（视为"避免损失"，从严） | 0.4 | 14.4 万 | 20.8 个月 |

**两个都合法。** 这正是不能交给系统判的原因——它取决于这笔钱在客户账上到底怎么走。但放任自由会毁掉跨项目可比性，所以配套三条：

| 兜底机制 | 做法 |
|---|---|
| 强制留痕 | `realization_note` 必填，报告里逐条印出来 |
| 双口径呈现 | 客户交付物同时给理论值和可实现值，不只给一个 |
| 定期校准 | 每季度拉一次全员 `realization_mode` 分布，同一类场景判得差太远的，开会拉齐 |

> **一条经验：凡是不该由系统判的地方，系统就别判；但一定要把"谁在什么时候、基于什么理由判的"钉在数据里。** 否则三个月后复盘时，没有人认账，模型也学不到东西。

**`realization_factor` 与传导链的关系（v2.1 补充）：**

`realization_factor` 是**结果**，不是输入。它必须等于 §4 传导链上各段 `mult_base` 的乘积：

```
realization_factor = ∏ mult_base   （由 R5-C12 强制校验，容差 0.005）
```

所以 OP-01 的 `realization_factor` 不再是手填的 `0.6`，而是 `1.00 × 0.95 × 0.70 × 0.90 = 0.5985`。报告里显示为"0.60（四舍五入）"，但库里存 0.5985。

| 之前 | 现在 |
|---|---|
| 顾问填 0.6，凭经验 | 顾问填各段系数，系统连乘 |
| 客户问"凭什么 0.6"，答不出 | 逐段可答、可质疑、可验 |
| 改了一段忘了改总系数 | C12 直接拦截 |

> 如果某段还没填，`realization_factor` 就是空——这正好和 §6.1 的"全有或全无"对上：**链条没画完，就没有总系数；没有总系数，就出不了回本周期。**

### 6.2 这个改动会让结论变难看（但更真实）

用 OP-01 重算：

| 口径 | 年化收益 | 回本周期 |
|---|---|---|
| 理论值（v1） | 29 万 | 16.6 个月 |
| 可实现值（v2，系数 0.5985） | **17.4 万** | **27.6 个月** |

一期三个机会点分别按各自的实现形态折算：

| 机会点 | 实现形态 | 系数 | 理论收益 | 可实现收益 | 回本（v1→v2） |
|---|---|---|---|---|---|
| OP-01 订单录入 | 不增人 | 0.5985 | 29 万 | 17.4 万 | 16.6 → **27.6** 个月 |
| OP-02 费用追收 | 直接增收 | 1.0 | 36 万 | 36 万 | 8.3 → 8.3 个月 |
| OP-03 单证核对 | 不增人 | 0.5985 | 15 万 | 9 万 | 9.6 → **16.0** 个月 |
| **一期组合** | — | — | 80 万 | **62.4 万** | 11.6 → **14.8** 个月 |

> **注意一个反直觉的结果：一期组合的回本只从 11.6 个月变成 14.8 个月，但 OP-01 单片从 16.6 个月恶化到 27.6 个月。**
>
> 原因是一期里还包含 OP-02（费用追收是**真金白银的现金**，不打折）。这带来一个重要的策略含义：
> **如果只做 OP-01，回本很难看；做成"OP-01 + OP-02"的组合，故事才成立。**
> 这恰好解释了为什么诊断阶段要算组合 ROI，而不是只推荐单个机会点。

**这不是模型的错，是原来算得太乐观。**

建议的呈现方式：**对外同时展示两个数字**，并明确说明差异原因。这比藏起来更可信，也更能建立长期信任——尤其是当客户后来自己算出来的时候。

**这也解释了为什么 AI 项目 ROI 普遍被高估：大家算的都是理论值。**

### 6.5 `limitations` · 局限条目的分级（P5 决策）

**解决什么问题：** v2 的"本次诊断的局限"是自动汇总出来的 5 条，读起来像律师写的免责声明——客户会跳过，而其中最重要的那条（"36 万未验证"）正好被稀释在里面。

**已定决策（v2.1）：按"影响什么"三分法，内部项不进客户文档。**

```sql
CREATE TABLE limitations (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  engagement_id  uuid NOT NULL REFERENCES engagements(id) ON DELETE CASCADE,

  -- 来源：由 R5-C6 自动汇总，也可顾问手工补充
  source_type    text NOT NULL CHECK (source_type IN
                   ('baseline_low_confidence','client_financial','gate_gap',
                    'benchmark_uncalibrated','manual')),
  source_id      uuid,                  -- 指向 baselines / client_financials 等

  title          text NOT NULL,         -- '异常费用漏收率未经抽样验证'
  detail         text NOT NULL,         -- 说明 + 建议动作
  affected_refs  text[] NOT NULL DEFAULT '{}',  -- 影响的机会点编号

  -- 分级：决定它出现在客户文档的哪一部分
  impact_class   text NOT NULL CHECK (impact_class IN
                   ('amount','scope','method','internal')),
  severity       int NOT NULL DEFAULT 1 CHECK (severity BETWEEN 1 AND 3),

  created_at     timestamptz NOT NULL DEFAULT now()
);
```

**四类的去处（这是 P5 的核心）：**

| `impact_class` | 影响什么 | 出现在哪 | 排版要求 |
|---|---|---|---|
| `amount` | **金额判断**（收益/回本数字是否可信） | **正文独立小节**，放在 ROI 章节之后 | 加粗标题；每条必须写"这个数字在验证前不得对外承诺" |
| `scope` | **范围完整性**（是否有环节没覆盖、可能漏机会点） | 正文，紧跟痛点清单 | 简洁列出缺哪类角色/环节 |
| `method` | 方法与口径（对标未校准、抽样样本量） | 附录 | 正常排版，不加重 |
| `internal` | 内部管理项（门禁未过、待补录、交付风险） | **只进系统，不进客户文档** | — |

**为什么 `internal` 必须剔除：**

"痛点只有 8 条，未达 G1 要求的 10 条"——这是**内部质量指标**，不是客户需要知道的信息。写进客户报告只有两个效果：让客户怀疑诊断做完了没有，或者显得我们在凑数。

但它在系统里必须留着，因为 C11 需要它。**同一份数据，两个读者，两种呈现。**

**新增两条校验：**

> **R5-C13：`impact_class='internal'` 的条目不得出现在客户交付物中。**
> 实现方式：模板渲染时按 `impact_class` 过滤，而不是靠顾问手动删。这样"忘了删"不可能发生。
>
> **R5-C14：所有 `impact_class='amount'` 的条目必须出现在正文，且顺序在对方 `affected_refs` 的 ROI 章节之后。**
> 顺序是硬要求——局限必须紧跟在它质疑的那个数字后面，不能堆到文末。

**效果对比：**

| | 改之前 | 改之后 |
|---|---|---|
| 位置 | 第 10 节，5 条平铺 | 金额类进 ROI 章后；范围类进痛点章后；方法类进附录 |
| 读者感受 | "免责声明，跳过" | "他们主动告诉我哪个数字还不牢" |
| 最重要那条 | 被稀释成 1/5 | 独立成节，加粗 |
| 内部项 | 混在客户文档里 | 不进客户文档 |

> **一条经验：局限不是越多越诚实，而是"该在哪出现就在哪出现"。** 把 5 条堆一起，效果等于 0 条。

## 7. 规则 R5 · 生成前一致性校验

### 7.1 为什么需要

写 04 的样例时，发现了三处数字不自洽：回本周期串了、门禁 76% 却标记通过、通过数算错。**这些都是跨表一致性缺失导致的，不是笔误。**

### 7.2 DDL

```sql
CREATE TABLE consistency_checks (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  deliverable_id uuid NOT NULL REFERENCES deliverables(id) ON DELETE CASCADE,
  check_code     text NOT NULL,
  level          text NOT NULL CHECK (level IN ('block','warn')),
  passed         boolean NOT NULL,
  detail         jsonb,
  checked_at     timestamptz NOT NULL DEFAULT now()
);
```

### 7.3 校验清单

| 编号 | 检查 | 级别 | SQL 要点 |
|---|---|---|---|
| **C1** | 进入方案设计的机会点必须有基线 | block | `LEFT JOIN baselines ... WHERE b.id IS NULL` |
| **C2** | 报告汇总数 = 明细之和（容差 0） | block | 应用层重算比对 |
| **C3** | 门禁状态与 checklist 一致 | block | 同一数据源，防止缓存漂移 |
| **C4** | 痛点数达到门禁要求 | **动态**（见 C11） | `actual / required` 分级 |
| **C5** | killed/parked 的机会点不得出现在"推荐路线" | block | 状态白名单过滤 |
| **C6** | 所有 `confidence='low'` 的基线必须在"局限"章节出现 | block | 差集比对 |
| **C7** | 引用的 benchmark 存在且 `year >= 当前年-2` | warn | 过期则提示 |
| **C8** | `requires` 依赖无环 | block | 递归 CTE |
| **C9** | `deliverables.template_id` 存在 | block | 模板注册表 |
| **C10** | ROI 收益形态已选定并署名确认 | block | `realization_confirmed_at IS NULL` |
| **C11** | 门禁量化项缺口分级 | 动态 | `actual/required < 0.5` → block；`< 1.0` → warn |
| **C12** | 传导链乘积 = `realization_factor` | block | `abs(∏ mult_base − factor) > 0.005` |
| **C13** | `internal` 类局限不得出现在客户文档 | block | 模板渲染时按 `impact_class` 过滤 |
| **C14** | `amount` 类局限必须出现在正文，且紧跟对应 ROI 章节 | block | 渲染顺序断言 |

### 7.3.1 C11 · 缺口比例分级（已定）

痛点数量不足要不要拦，取决于**缺多少**。规则统一如下，适用于所有带量化阈值的门禁项（痛点数量、盘点完成度、访谈人数……）：

```
ratio = actual / required

ratio >= 1.0        → pass
0.5 <= ratio < 1.0  → warn    （允许生成，文档末尾附"数据待确认"清单）
ratio < 0.5         → block   （拒绝生成）
```

**对本次样例的影响：**

| 门禁项 | 要求 | 实际 | ratio | 级别 | 结果 |
|---|---|---|---|---|---|
| 痛点数量 | 10 | 8 | 0.80 | warn | 放行，附待确认清单 |
| 四维盘点完成度 | 80% | 76% | 0.95 | warn | 放行，附待确认清单 |

两项都是 `warn`，**报告可以生成**。但如果痛点只有 4 条（ratio 0.4），就会直接拦下——那已经不是"补充一下"，而是"诊断还没做完"。

> **为什么不用一刀切 block：** 8/10 的报告对客户仍有价值，硬拦会逼顾问伪造痛点凑数——那比缺 2 条糟糕得多。分级的作用是**在"还能用"和"不能用"之间划一条线**，而不是制造凑数动机。

### 7.3.2 C10 从 warn 升为 block（P1 决策的连带影响）

因为 `realization_mode` 不再有默认值，**"没选"是一个明确可检测的状态**（`realization_confirmed_at IS NULL`）。这种状态下所有回本周期都算不出来，生成报告没有意义。

> 原来定 warn 是因为"默认值 revenue"会让漏填看起来像填了。去掉默认值之后，漏填变成显式空值，就能理直气壮地 block。

### 7.3.3 C12 · 链条与总系数必须对得上（P4 决策的连带影响）

P4 把敏感度改成传导链之后，`realization_factor` 从"输入"变成了"输出"。这带来一个新的作弊路径：**链条画得漂亮，总系数还是原来那个拍出来的数。**

C12 就是堵这个：

```sql
-- 任一机会点：链条乘积必须等于记录的 realization_factor
SELECT s.opportunity_id,
       round(exp(sum(ln(s.mult_base))), 4) AS chain_product,   -- 连乘
       r.realization_factor,
       abs(exp(sum(ln(r2.mult_base))) - r.realization_factor) AS diff
  FROM roi_sensitivity s
  JOIN roi_models r ON r.opportunity_id = s.opportunity_id
 GROUP BY s.opportunity_id, r.realization_factor
HAVING abs(exp(sum(ln(s.mult_base))) - r.realization_factor) > 0.005;
```

> 用 `exp(sum(ln()))` 而不是 `prod()`——PostgreSQL 没有内置 `prod` 聚合，虽然可以自定义，但没必要为一次校验写扩展。
> 注意 `mult_base = 0` 时 `ln(0)` 会报错，需要先过滤或改用 `FILTER (WHERE mult_base > 0)`。

### 7.3.4 C13 / C14 · 局限的分流（P5 决策的连带影响）

这两条不是"数据对不对"的校验，是**"该不该给这个读者看"的校验**。放在 R5 里是因为它们同样必须在生成前生效——靠顾问记得删掉内部项，迟早会漏。

```
渲染流程：
  limitations 按 impact_class 分组
    ├─ internal → 丢弃（只写 consistency_checks，供内部查看）
    ├─ amount   → 正文，插在 affected_refs 对应的 ROI 章节之后
    ├─ scope    → 正文，插在痛点清单之后
    └─ method   → 附录「方法与口径」
```

> **实现要点：过滤发生在模板层，不是靠人。** 否则每次生成都要有人检查一遍漏没漏，等于没做。

### 7.4 执行时机

```
POST /api/deliverables/generate
  ↓
1. 读取 engagement 全部结构化数据
2. 跑 14 项 consistency_checks
3. 有任何 block 级失败 → 拒绝生成，返回失败清单
4. 仅 warn 级失败 → 允许生成，但在文档末尾附"数据待确认"清单
5. 生成 → 写 generated_snapshot → 记录 checks 结果
```

**关键：block 级失败时，系统必须拒绝生成，而不是警告后继续。** 否则规则形同虚设。

### 7.5 校验结果如何呈现

## 8. 对自动化率的影响

| 章节 | v1 | v2.2 | 提升来源 |
|---|---|---|---|
| 业务现状 | 60% | **85%** | process_nodes 生成流程图 |
| 四维诊断 | 55% | 60% | is_implicit 单列一节 |
| ROI 测算 | 95% | **100%** | 传导链自动连乘 + 单段恶化自动算 |
| 摘要 | 70% | 75% | benchmark 定位可自动 |
| 推荐路线 | 30% | 35% | dependency 可自动排序 |
| 局限说明 | 80% | **100%** | limitations 按类自动分流，顾问只填内容 |
| **整体** | **62%** | **约 80%** | |

**剩下的 20% 是什么：** 判断。推荐路线里"为什么不是它"、风险应对措施、流程图的节点颗粒度——这三样永远不要自动化。

> **P4/P5 各贡献了约 1 个百分点，但价值不在百分比。**
> 传导链让"0.6 哪来的"从答不出变成逐段可查；局限分流让客户只看到该看的 5 条中的 2 条。
> **这两件事提升的是可信度，不是自动化率。**

## 9. 迁移顺序

```
第 1 步（无依赖，可并行）
  ├─ benchmarks
  ├─ client_financials
  ├─ limitations
  └─ consistency_checks

第 2 步（依赖 opportunities / roi_models）
  ├─ opportunity_dependencies
  └─ roi_sensitivity   ← v2.2 的 stage 序号是 NOT NULL，
                          存量数据必须一次性补齐，不能分两次上线

第 3 步（独立模块）
  └─ process_models / process_nodes / process_edges

第 4 步（字段变更，ALTER）
  ├─ roi_models：realization_mode / realization_factor / realization_note
  │              / realization_confirmed_by / realization_confirmed_at
  │              / realized_value
  ├─ inventory_items：is_implicit / discovered_by
  └─ deliverables：template_id / template_version / generated_snapshot

第 5 步（数据回填 + 强制补录）
  ├─ 存量 ROI 一律留空（不填默认值）
  ├─ 把 realization_confirmed_at IS NULL 的 ROI 列成「待补录清单」
  │   → 分派给原项目负责人，30 天内补录完
  └─ 存量机会点按行业默认值补 dependencies（可空）
```

**注意第 5 步和第 2 版草稿的差别：**

v2.0 草稿写的是"存量 ROI 默认 'revenue'，factor=1.0"。按 P1 的决策，这条**必须删掉**——一旦回填默认值，历史项目就会全部显示成"直接增收、不打折"，回本周期凭空变好，而没有任何人做过这个判断。这正是"默认值漂移"最典型的翻车方式。

改成"留空 + 待补录清单"会多花一点人力（本案 6 张 ROI 卡），但换来一个干净的事实：**系统里每一个 ROI 数字，都能追到一个人和一句话理由。**

**回滚风险：** 第 4 步的 `realized_value` 是生成列，回滚需要先 drop column；`realization_all_or_nothing` 约束在回滚时也要一并 drop。建议先在 staging 验证。
