# AI 能力路线图

> 目的：回答“AI 还能在哪些业务节点发挥作用、什么时候做、需要什么前提”。
> 结论：AI 的价值分五层——**感知 → 预测 → 优化 → 生成 → Agent**。
> 当前完成的是“感知/结构化”的一部分；预测与优化是下一阶段，Agent 最后。
> 适用：对内排期 + 对外讲清边界，避免把规则/系统功能包装成 AI。

---

## 一、五层能力：AI 不只是“大模型”

| 层 | 做什么 | 主要技术 | 当前状态 | 典型节点 |
|---|---|---|---|---|
| **感知 / 结构化** | 图片、PDF、聊天、表格 → 结构化数据 | OCR + 大模型 + 规则 | 🟩 A3、P4 已跑通 | 托书解析、发票识别 |
| **预测** | 预测时间、成本、回款、需求、风险 | 统计 / 机器学习 | ⬜ 未做 | ETA、回款概率、现金流、运力 |
| **优化** | 在约束下求最优解 | 运筹优化 + 机器学习 | ⬜ 未做 | 派车、路线、装载、信用、定价 |
| **生成 / 辅助** | 写报告、解释、问答、审阅 | 大模型 + 领域数据 | 🟡 少量 | 异常解释（可选模型）、催收话术润色（可选，默认关闭）、经营问答（诊断平台内部） |
| **Agent / 执行** | 跨系统自动操作 | 工具调用 + 审批 + 审计 | ⬜ 不建议现在做 | 自动派车、自动对账、自动催收 |

> 注意：**优化类大多是运筹学/机器学习，不一定用大模型。** 不要把所有 AI 都等同于 LLM。
> 催收话术默认是**分档模板 + 占位符替换**；可选的 AI 润色只改措辞，数字由规则注入、人工核对后才复制，
> 默认关闭。按回款历史个性化生成仍未做。

```mermaid
flowchart LR
  P0["P0 感知/结构化<br/>托书、发票"] --> P1["P1 规则自动化 + 生成辅助<br/>对账、账龄、异常解释"]
  P1 --> P2["P2 预测<br/>回款、ETA、成本、运力"]
  P2 --> P3["P3 优化<br/>派车、路线、信用、定价"]
  P3 --> P4["P4 Agent<br/>自动执行 + 审批"]
```

## 三、分期路线

### P0 · 已完成：感知 + 规则

- A3 托书解析：OCR + 大模型 + 规则
- P4 发票识别/校验：OCR + 大模型 + 规则
- R2 对账、R5 账龄、P1 外协结算、C6 异常费用：规则自动化
- 交付平台：多租户、RLS、审计、套餐/账单

### P1 · 0–3 个月：数据地基 + 生成辅助

目标：把“能读的”扩展，把“能解释的”补上。

- 合同 / 对账单 / 结算单 / 维修单抽取
- 对账差异解释：不只报差额，解释“可能原因”
- 催收话术模板：按账龄分档 + 占位符替换（✅ 已完成）；可选 AI 润色只改措辞、数字由规则锁定（默认关闭）
- 费用科目映射：为 S1 成本归集做准备
- 经营问答：基于指标层的内部助手
- 指标：单据覆盖率、自动通过率、修正率、解释采纳率

### P2 · 3–6 个月：预测

目标：用历史数据回答“接下来会怎样”。

- 回款概率 / 现金流预测
- ETA / 到港时间预测
- 成本异常归因（从“差异”到“原因”）
- 报价建议（辅助）
- 运力预测
- 平台侧项目延期/续约风险预测

> 先规则 + 简单模型，再上复杂模型；预测结果必须可解释。

### P3 · 6–12 个月：优化

目标：在约束下给“推荐方案”，人确认后执行。

- 推荐派车：车辆-订单匹配、路线、装载
- 路线/空驶优化
- 动态信用额度 / 催收策略
- 定价优化
- 成本归集 + 单车毛利（通用页 `/margin` 已做；真实费用数据待客户）
- 交付资源排期

> 优化不是“买一个模型”，是数据 + 约束 + 目标函数 + 组织协同。

### P4 · 12 个月以后：Agent

目标：在低风险、高重复的场景自动执行。

- 自动对账 / 自动催收提醒
- 自动派车（需调度员审批）
- 自动生成并发送对账单

**Agent 四条护栏：**

1. 人工审批或限额
2. 全量审计与回滚
3. 明确失败降级
4. 先内部、后客户

## 四、候选能力落地门槛

| 候选 | 价值 | 数据前提 | 组织前提 | 技术 | 第一步 |
|---|---|---|---|---|---|
| 推荐派车 | 降空驶、提准时率 | 运单、车辆、司机、GPS、港口 | 调度员信任 | 运筹 + 预测 | 推荐模式，人工确认 |
| 回款预测 | 缩短回款周期 | 12–24 个月应收/回款 | 财务认可口径 | 分类/回归 | 规则 + 简单模型 |
| 报价建议 | 提高赢单/毛利 | 历史报价、赢单、成本 | 销售愿意用 | 回归 + 优化 | 辅助报价 |
| 成本归集 | 单车毛利 | 油卡/路桥/维修 + 运单映射 | 财务/车队配合 | 规则 + 映射 | 先做科目映射 |
| ETA 预测 | 客户体验/调度 | GPS、港口、历史 | 数据共享 | 时序模型 | 历史回测 |
| 异常归因 | 直接省钱 | 费用明细、科目 | 财务复核 | 规则 + LLM 解释 | 先规则后解释 |
| 经营问答 | 管理层决策 | 指标层 | 指标口径统一 | LLM + 语义层 | 内部试用 |
| 合同/对账单抽取 | 减少录入 | 文档样本 | 业务确认 | OCR + LLM | 扩展现有底座 |
| Agent 自动执行 | 降人力 | 数据 + 工具 + 权限 | 信任 + 审计 | 工具调用 | 暂不做 |

## 五、数据飞轮

```mermaid
flowchart LR
  D1["单据/聊天/图片"] --> D2["结构化数据"]
  D2 --> D3["规则校验与业务系统"]
  D3 --> D4["历史数据沉淀"]
  D4 --> D5["预测模型"]
  D5 --> D6["优化建议"]
  D6 --> D7["人工确认/执行"]
  D7 --> D4
```

- A3/P4 是飞轮的入口：每多一个客户，多一批结构化样本
- 没有 D1→D2，后面的预测/优化都是空中楼阁
- 预测/优化又会产生新的标注数据，反哺模型

## 六、对客户怎么说

1. **“现在做的是数据入口，不是 AI 替代人。”**
   AI 把微信/图片/发票读成数据；规则和系统负责算得准、管得住。
2. **“下一阶段用你的历史数据做预测和优化，先推荐、后自动。”**
   调度、回款、报价都可以做，但需要数据和试点。
3. **“优化不是买一个模型，是数据 + 规则 + 运筹 + 组织协同。”**
   先定口径、拿数据、选 1–2 个指标，再谈自动。

**需要客户提供：**

- 历史运单/订单/车辆/司机/GPS
- 应收/回款/合同/费用明细
- 一个能拍板的业务 owner
- 一个可量化的试点指标（准时率、空驶率、回款天数、单票成本）

---

## 七、边界：不要做什么

- 不要让大模型算金额、账龄、税务、法律结论
- 没有数据不要承诺调度优化；单车毛利只能做通用演示，不能承诺客户结论
- 没有审批/审计不要做 Agent 自动执行
- 不要把规则/系统功能包装成“AI”
- 不要一次做全流程；一次只验证 1–2 个指标

## 八、下一步优先级

| 优先级 | 事项 | 原因 |
|---|---|---|
| 1 | 合同/对账单抽取 + 对账差异解释 | 复用现有 OCR/LLM 底座，直接减少录入与核对 |
| 2 | 回款预测（催收话术模板与可选润色已做；按历史个性化未做） | 数据已有基础，价值可量化 |
| 3 | 成本归集（先科目映射） | 单车毛利的前置，等客户数据 |
| 4 | 推荐派车试点 | 价值高，但需要运单/车辆/GPS 和组织配合 |
| 5 | 经营问答 / 知识库 | 低风险、易演示，但别当核心卖点 |
